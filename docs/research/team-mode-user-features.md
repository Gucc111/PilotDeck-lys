# Team 模式用户功能清单

> 基于 dsh-agent-team 的用户视角功能提取（2026-10-14）
> 本文档只描述用户可感知、可操作的功能，剥离所有技术实现细节
> 本文保留调研时 DSH 已实现功能，不能据此判断 PilotDeck 的实现。下文明确标注 PilotDeck 的小节是产品差异说明；其他“当前版本”、按钮和限制均指 DSH。

## PilotDeck 当前用户流程（有意区别于 DSH）

1. 在侧栏“团队 / Teams”配置 Leader、Teammate 和 Team；在聊天输入框右下角的模型/Team 下拉菜单选择 Team 的显示名称。PilotDeck 不使用下文 DSH 的蓝图创建入口、运行预设或动态成员实例管理。
2. 在同一根会话向 Leader 提出任务。Leader 使用异步委派组织成员；Teammate 给其他 Teammate 的普通协调消息仍先到 Leader，由 Leader 明确 relay。
3. Teammate 请求工具权限、调用 `ask_user_question` 或退出 Plan 模式时，用户点击与“团队详情”并列的“团队交互”。Leader 不接收、转发或代答这三类请求。
4. 面板按 Teammate 分卡，每张卡只显示名字、角色、状态和“查看聊天”。三类可展开区分别列出简短通知；点击后打开普通会话对应的交互卡片。允许/拒绝、回答/取消、批准/拒绝 Plan 后都保留处理时间和历史；提交失败仍保持待处理并提示重试。
5. 点击“查看聊天”只读查看该成员的历史和流式内容，没有输入框或普通会话操作。浏览器刷新、直接 URL、断线重连恢复同一份 transcript，不另建成员聊天或调用模型。
6. 浏览器刷新和 WebSocket 重连恢复交互记录。停止 Team 时未处理请求取消；Gateway 重启时失去等待句柄的请求过期，均保留历史，不能点击后继续执行。Leader 自身的权限、问题和 Plan 仍在主聊天原有卡片处理。

PilotDeck 当前不含 DSH 治理模式、动态权限调整、管理员审批、Gantt 时间线和成员归档/处置等能力。完整说明见 [PilotDeck Team 使用说明](../team-mode.md)，实际验收见 [测试用例](../testing/team-mode-e2e-acceptance.md)。

## DSH 参考功能与局部 PilotDeck 对照

---

## 1. 团队创建与配置

### 1.1 创建新团队

- **入口**：点击侧边栏底部"新建团队"按钮
- **选择蓝图**：从下拉列表选择预定义的团队模板（例如"研发团队"、"内容团队"）
- **选择工作区**：指定团队工作的文件夹位置
- **选择运行预设**：决定团队 AI 的基础工具集和人格组合方式（切换预设会自动重新做兼容性检查）
- **（可选）初始任务**：创建时可以直接给 Leader 分配第一个任务
- **（可选）上下文交接**：从当前会话"继承"背景信息到新团队（"从此处开始团队"）

### 1.2 兼容性检查

创建前系统会自动检查：

- ✓ **就绪**：可以直接创建
- ⚠ **警告**：缺少某些能力但可以继续（需要勾选"我已了解降级"）
- ✕ **无法创建**：缺少必需能力，创建按钮禁用

### 1.3 团队蓝图

- 蓝图是预先定义的团队配置文件（YAML 格式）
- 定义了团队有哪些角色（Leader + 成员模板）
- 定义了每个角色的职责描述、可用工具、权限范围
- 用户可以在文件系统中管理蓝图，通过"刷新蓝图目录"立即生效
- 同一个蓝图可以创建多个团队实例

## 2. 团队成员管理

### 2.1 Leader（领队）

- 每个团队有且只有一个 Leader
- Leader 就是你打开的那个会话窗口
- Leader 负责协调所有成员、分配任务、做决策

### 2.2 成员（Member）

**创建成员**：
- 在团队视图中，每个成员模板下有"+"按钮
- 填写成员标签（名字）、可选分组标签、可选工作区
- DSH 成员创建后拥有独立会话。**PilotDeck 对照**：成员使用 Team 内部执行上下文，从团队交互面板的 **查看聊天** 打开只读流式视图

**成员状态**：
- 🟡 **已创建**：刚创建，还没开始工作
- 🔵 **运行中**：正在执行任务
- 🟢 **已结算**：任务完成，等待新工作
- 🟢 **已归档**：暂时停用（可恢复）
- ⚫ **已处置**：永久停用（历史记录保留）

**成员操作**：
- **发送任务**：给已结算的成员分配新工作
- **发送跟进**：向运行中的成员追加指令
- **发送消息**：通过团队协作操作提交普通协调消息；Teammate 人类交互请求不从该入口代答
- **归档**：暂停成员（会先停止当前工作）
- **恢复**：重新激活已归档的成员
- **处置**：永久停用成员

### 2.3 工作模式

工作模式由蓝图中的角色模板决定，创建成员时界面会提示当前模板属于哪一种。

**持久化成员**（默认）：
- 每次任务都使用同一个成员
- 成员记住之前的对话历史
- 适合需要上下文延续的工作

**一次性成员**：
- 每次任务创建一个新成员
- 成员之间互不干扰
- 适合独立的、可并行的任务

## 3. 任务委派与协作

### 3.1 Leader 委派任务

**同步模式**（等待结果）：
- Leader 发出任务后会等待成员完成
- 适合需要立即知道结果的场景

**异步模式**（后台执行，默认）：
- Leader 发出任务后立即继续工作
- 成员在后台独立执行
- 完成后 Leader 会收到通知
- Leader 可以用"收集结果"查看任务状态

### 3.2 任务跟踪

- 每个任务有唯一的追踪令牌
- Leader 可以随时查询任务状态：运行中 / 成功 / 失败
- 可以通过令牌查看任务详细结果

### 3.3 成员间协作

**成员发消息给 Leader**：
- 成员可以随时向 Leader 汇报、求助
- 消息直接送达 Leader

**成员发消息给其他成员**：
- 消息先发给 Leader，并标注"本意是发给某某成员"
- 由 Leader 决定是否转发、如何转发（系统不会自动转发）

### 3.4 进度报告

成员可以主动报告工作进度：
- 📍 **进行中**：任务还在执行
- ✅ **已完成**：任务完成
- 🚫 **受阻**：遇到问题

Leader 和用户都能在"活动与进度"面板看到所有成员的当前状态。

## 4. 权限与审批

### 4.1 DSH 权限等级

从低到高：**Teammate < Leader < 人类用户 < 管理员**。PilotDeck 不采用成员请求由 Leader 审批的链路。

### 4.2 PilotDeck 差异：人类交互流程

**Teammate 直接请求人类处理**：
- 工具调用命中询问规则时，直接进入团队交互 → 工具调用权限询问
- 调用 `ask_user_question` 时，直接进入团队交互 → 向用户提问
- 调用 `exit_plan_mode` 时，直接进入团队交互 → Plan 授权执行
- Leader 不接收、转发或代答这些请求

**Leader 请求人类审批**：
- Leader 自己的权限询问仍使用 Leader 主聊天已有的交互卡片

**人类处理**：
- 入口与团队详情并列，按 Teammate 展示待处理和已处理记录
- 点击通知行打开对应普通交互卡片，结果和状态始终保留

### 4.3 权限调整

**人类在界面中可以做的**：
- 在治理面板的"生效配置"区域，为某个成员设置或重置能力覆盖：模型、工具、技能、外部服务各自的允许/拒绝
- 在"权限管理"区域查看某个成员当前生效的文件访问规则和命令执行规则，以及每条规则的来源

**Leader 可以做的**：
- 通过自己的工具为某个成员授予或撤销文件访问规则、命令执行规则
- 收紧立即生效；放宽受蓝图设定的上限约束，超出上限会被直接拒绝

### 4.4 权限范围

**文件操作权限**：
- 读取文件
- 写入/编辑文件
- 限定在特定目录

**命令执行权限**：
- 执行 shell 命令（bash / PowerShell）
- Leader 执行命令：蓝图在两处同时授权时自动放行，否则转为人类审批
- Teammate 执行命令：按角色策略直接执行、拒绝或向人类询问

**工具权限**：
- 每个成员可用的工具集由蓝图定义
- 人类可以在运行时通过能力覆盖收紧或放宽

## 5. 团队视图与监控

### 5.1 PilotDeck 视图入口

- 打开团队会话后，使用与“团队详情”并列的“团队交互”入口
- 团队交互按钮显示待处理总数；团队详情负责配置及运行状态

### 5.2 时间线（Gantt 图）

- 显示每个成员的工作时间轴
- 每条横杠代表一段运行时间
- 可以缩放（滚轮 / +/- 键）和拖动查看
- DSH 点击横杠可打开成员会话；PilotDeck 不提供此时间线，使用团队交互中的只读“查看聊天”
- 鼠标悬停显示时长和状态

### 5.3 成员列表

**Leader 组**：
- 显示 Leader 状态和活跃成员数
- 按钮：以 Team 模式打开、以普通模式打开

**成员组**（按模板分组）：
- 每个模板一组，显示该模板的成员数
- "+"按钮创建新成员
- 每个成员行显示：
  - 状态指示点（颜色 + 状态词）
  - 当前动作或"暂无动作"
  - 待处理数量徽章（权限询问、用户问题、Plan 授权）
  - 操作按钮（发送任务/消息/归档/恢复/处置）

### 5.4 治理面板

**兼容性状态**：
- 显示当前团队与环境的兼容性（兼容/降级/需要处理/结构性错误）
- 显示警告、致命问题、已确认项的数量和最后检查时间
- 可以重新检查兼容性

**策略状态**：
- 显示当前团队的运行治理模式
- 可以切换不同的策略模式
- 每种模式锁定不同的能力开关

**生效配置**：
- 查看每个成员当前使用的 AI 模型
- 查看每个成员当前可用的工具列表
- 查看权限覆盖记录

**PilotDeck 团队交互（独立入口，不是 DSH 治理面板）**：
- 只列 Teammate 卡片和三个可展开区域：工具调用权限询问、向用户提问、Plan 授权执行
- 点击行后复用普通会话交互卡片，处理后仍显示历史状态
- 刷新、重连或直接打开 URL 时从服务端记录恢复

**权限管理**：
- 查看某个成员当前生效的权限规则
- 查看权限来源（蓝图默认/Leader 授予）
- 查看规则一致性诊断

### 5.5 活动与进度

- 显示所有成员当前正在做什么
- 每条活动显示：状态点、主题、负责人、摘要
- 自动定期刷新，也可以手动点"刷新团队视图"

### 5.6 团队事件（台账）

- 所有团队协作的完整时间线
- 类型过滤器：全部/团队/成员/生命周期/消息/控制/策略/兼容性/进度
- 成员过滤器：只看某个成员的事件
- 每条事件显示：时间、类型、参与者、摘要、状态
- 待裁决的控制请求可以展开：
  - 查看完整请求参数
  - 查看请求理由
  - 允许或拒绝

## 6. 团队生命周期

### 6.1 打开已有团队

在团队视图的零状态区域可以看到"已持久化的团队"列表：
- 显示团队的蓝图、工作区、成员数、创建时间
- 可以选择"以 Team 模式打开"（完整团队功能）
- 可以选择"以普通模式打开"（当成普通会话，不加载团队）

### 6.2 重启恢复

系统重启后：
- 所有团队和成员的配置都保留
- 所有历史记录都保留
- 成员不会自动唤醒（避免资源浪费）
- Leader 可以通过"发送任务"手动恢复成员工作
- 普通任务通知不会重发，Leader 用"收集结果"恢复任务状态
- **PilotDeck 对照**：Teammate 人类交互记录由团队交互面板恢复；浏览器刷新/断线保留 pending，Gateway 重启后未处理记录标记过期并保留历史
- **PilotDeck 对照**：Teammate 只读聊天直接读取原运行段 transcript，不创建新会话或发起模型调用

## 7. 设置与偏好

### 7.1 运行预设

- 创建团队时选择的预设决定团队 AI 的基础工具集和人格组合方式
- 预设列表来自系统已配置的预设，不同预设暴露的基础工具不同
- 如果蓝图对成员权限限制很严格，建议选择工具最少的"最小"预设，否则可能因为存在无法纳入管理的工具而无法创建团队（见 8.3）

### 7.2 模型选择

- 蓝图可以为每个角色指定推荐的 AI 模型
- 运行时可以覆盖模型选择（在治理面板）
- 不同成员可以使用不同模型

## 8. 限制与已知问题

### 8.1 当前限制

- **无管理员审批通道**：某些需要"管理员"批准的请求会直接拒绝
- **成员不能直接通信**：成员之间的消息一律经过 Leader 转发，没有开放直连设置
- **DSH 通知恢复限制**：控制通知不会补发，需要查询记录。PilotDeck 另用持久化交互记录恢复/失效请求，不依赖 Leader 查找
- **审批完成后 Leader 可能被反复唤醒**：已知问题，尚未修复
- **创建后出现的兼容性警告无法在界面中逐项确认**：只能重新检查

### 8.2 UI 体验问题

- 团队事件列表很长时翻页较慢
- 某些状态需要手动刷新才能看到最新结果
- Dock 的"打开团队标签页"按钮目前无效

### 8.3 蓝图兼容性

- 某些严格权限配置的蓝图在默认预设上无法创建团队
- 需要使用"最小预设"或调整蓝图配置
- 自定义预设可能与某些蓝图不兼容

## 9. 典型使用场景

### 场景 1：研发团队并行开发

1. 创建"研发团队"（Leader + 3 个 Worker 成员模板）
2. Leader 将三个功能分别委派给三个 Worker（异步）
3. 三个 Worker 并行开发
4. 完成后 Leader 收到通知，逐一收集代码
5. Leader 整合代码并进行测试

### 场景 2：内容创作流水线

1. 创建"内容团队"（Leader + Researcher + Writer + Reviewer）
2. Leader 委派 Researcher 调研主题
3. Researcher 完成后，Leader 委派 Writer 撰写文章
4. Writer 完成后，Leader 委派 Reviewer 审校
5. Reviewer 提出修改建议，Writer 修订
6. Leader 收集最终稿件

### 场景 3：数据处理任务

1. 创建"数据团队"（Leader + 一次性 Worker 模板）
2. Leader 为每个数据文件创建一个新 Worker（一次性模式）
3. 多个 Worker 并行处理各自的数据文件
4. Worker 完成后自动通知 Leader
5. Leader 收集所有处理结果并汇总

### 场景 4：PilotDeck 差异——成员直接向用户请求决定

1. Teammate 需要删除文件，直接在团队交互 → 工具调用权限询问生成请求
2. 用户点击通知行，打开普通权限卡片并允许或拒绝
3. Teammate 需要补充发布环境时，在团队交互 → 向用户提问显示选项
4. Teammate 退出 Plan 模式时，在团队交互 → Plan 授权执行查看计划并批准或拒绝
5. 用户处理结果后，原 Teammate 继续或终止；Leader 不代答这些请求

## 10. PilotDeck 与普通会话的区别

| 维度 | 普通会话 | Team 模式 |
| --- | --- | --- |
| 对话窗口 | 1 个 | 1 个 Leader + N 个 Teammate 的只读聊天视图 |
| 任务执行 | 串行 | 可并行 |
| 权限管理 | 人类直接控制 | Teammate / Leader 发起，人类在对应交互入口处理 |
| 协作方式 | 无 | 消息、委派、审批 |
| 历史记录 | 单一聊天 | Leader 主聊天、成员只读 transcript、交互处理记录 |
| 适用场景 | 简单任务、探索式对话 | 复杂任务、多角色协作、并行工作 |

## 附录：概念速查

| 概念 | 用户理解 |
| --- | --- |
| **蓝图（Blueprint）** | 预定义的团队配置模板，像"招聘一个团队的职位描述" |
| **Leader** | 团队的协调者，你主要交互的那个会话 |
| **成员（Member）** | 团队中的执行者，各有专长和分工 |
| **模板（Template）** | 蓝图中定义的角色类型，如"研究员"、"开发者" |
| **实例（Instance）** | 从模板创建的具体成员，如"研究员 A"、"研究员 B" |
| **委派（Delegate）** | Leader 给成员分配任务 |
| **跟进（Follow-up）** | 向已经在工作的成员追加指令 |
| **收集（Collect）** | Leader 查询任务结果 |
| **审批（Approval）** | 权限不足时请求上级批准 |
| **归档（Archive）** | 暂停成员，可恢复 |
| **处置（Dispose）** | 永久停用成员 |
| **策略状态（Policy State）** | 团队当前的运行模式（非任务进度） |
| **兼容性（Compatibility）** | 团队配置与环境能力的匹配程度 |
| **治理（Governance）** | 权限、审批、策略的统称 |
