# Team 模式功能详解 · 模块 3：任务委派与协作

> 本文保留 2026-10-14 的 **DSH 参考产品调研**，不是 PilotDeck 的已实现功能清单。除明确标注“PilotDeck”的段落外，文中的“当前版本”、工具、按钮和限制均指调研时的 DSH。PilotDeck 使用说明见 [docs/team-mode.md](../../team-mode.md)。
> 上级文档：[Team 模式用户功能清单](../team-mode-user-features.md)

> **PilotDeck 当前实现边界**：普通 Team 协调消息仍采用 Leader relay；本篇中的动态成员管理、同步委派、治理和进度工具不因此成为 PilotDeck 的功能。Teammate 发起的权限询问、`ask_user_question` 和 `exit_plan_mode` 是面向人类的交互请求，直接进入团队交互面板，不作为成员间消息交给 Leader。

---

## 1. 这个模块解决什么问题

团队的日常运转靠 Leader：Leader 把任务拆开派给成员，跟踪进度，收集结果，在成员之间传话。本模块说明 Leader 手上有哪些工具、每个工具怎么用、任务从派出到完成经历什么、成员之间怎么通信。

人类用户的视角：你和 Leader 对话，Leader 自己决定调用哪些工具。你在团队视图里看到这些工具调用产生的效果（成员状态变化、事件记录、进度）。你也可以在团队视图里直接对成员做"发送任务 / 发送消息"，效果和 Leader 调工具相同。

---

## 2. Leader 的团队工具

Leader 会话里有 15 个以 `team_` 开头的工具。普通会话没有这些工具。蓝图可以通过 `capabilities.teamTools` 限制 Leader 看到其中哪几个。

### 2.1 查看类（只读，无副作用）

| 工具 | 作用 | 返回 |
| --- | --- | --- |
| `team_list_templates` | 列出蓝图定义的所有角色模板 | 每个模板的标识、显示名、工作模式 |
| `team_list_members` | 列出所有成员 | 每个成员的实例编号、模板、标签、状态、会话编号 |
| `team_inspect_config` | 查看一个成员的生效配置 | 模型、工具、技能、外部服务、文件权限规则、当前治理模式、环境要求状态 |
| `team_collect` | 查询已派出任务的结果（见第 4 节） | 每个任务：运行中 / 成功 / 失败 / 不可用 |
| `team_inspect`（PilotDeck 对应入口） | 读取成员名单及当前角色可见的任务、消息 | 当前运行成员、任务与消息摘要；完整 PilotDeck 工具表见使用说明 |

### 2.2 执行类（会改变团队状态）

| 工具 | 作用 | 关键参数 |
| --- | --- | --- |
| `team_create_member` | 创建一个新成员，不派任务 | 模板、标签、分组（可选）、工作区（可选） |
| `team_delegate` | 派任务：创建新成员并派，或派给已有成员 | 模板 **或** 成员编号（二选一）、标签、任务描述、附加材料（可选）、任务摘要（可选）、是否异步（默认是） |
| `team_follow_up` | 给已有成员追加任务（续用它的对话上下文） | 成员编号、任务描述、附加材料（可选）、任务摘要（可选）、是否异步（默认是） |
| `team_send_message` | 给一个成员发消息 | 成员编号、正文（最长 8192 字）、主题（可选） |
| `team_report_progress` | 记录某个成员某项工作的进度 | 成员编号、主题、进度（进行中 / 已完成 / 受阻）、摘要（可选） |
| `team_request_control` | 为某个操作发起审批请求 | 类型、目标成员、操作名 |
| `team_resolve_control` | 裁决一个审批请求 | 请求编号、决定（允许 / 拒绝 / 升级）、备注（可选） |
| `team_archive_member` | 归档一个成员 | 成员编号 |
| `team_grant_permission` | 给成员追加文件或命令权限规则 | 成员编号、规则列表 |
| `team_revoke_permission` | 撤销成员的权限规则 | 成员编号、规则列表 |

### 2.3 所有工具的共同约定

- **目标成员一律用实例编号**（形如 `inst-xxxx`），不能用名字或模板名。Leader 需要先 `team_list_members` 查编号。
- 每次调用带一个 Leader 自己生成的**请求令牌**。同一件事重试用同一个令牌，系统保证不会重复执行；不同的事必须用不同令牌。
- 每个工具返回的都是结构化结果，不抛异常。结果的 `status` 字段告诉 Leader 发生了什么：

| status | 含义 |
| --- | --- |
| `executed` | 执行了 |
| `delivered` | 消息已送达 |
| `progress-recorded` | 进度已记录 |
| `control-requested` / `control-resolved` / `control-escalated` | 审批相关 |
| `pending-control-listed` | 待审批列表已返回 |
| `permission-mutated` | 权限已变更（附带 `changed` 表示是否真的有变化） |
| `rejected` | 业务规则拒绝，附带错误码和原因（如配额超限、目标不存在、超出协作范围） |
| `blocked` | 被审批门拦住，附带原因和待审批的请求编号 |

- 工具可见不等于有权执行。蓝图的 `teamEnvelope` 决定 Leader 实际能做哪些协作动作；例如没有 `archive-member` 令牌时 `team_archive_member` 会返回 `rejected`。

### 2.4 Leader-only 的工具

以下工具只有 Leader 能用，成员即使看到也会被拒：

- `team_list_pending_control`
- `team_archive_member`
- `team_grant_permission`
- `team_revoke_permission`

## 3. 派任务：`team_delegate` 与 `team_follow_up`

### 3.1 两种派法

**派给新成员**（`team_delegate` + 模板）：

1. Leader 调 `team_list_templates` 看有哪些角色。
2. 调 `team_delegate`，指定模板、标签、任务描述。
3. 系统创建新成员并把任务交给它。

**派给已有成员**（`team_delegate` + 成员编号，或 `team_follow_up`）：

- 两者效果相同：把新任务交给一个已有成员，成员在自己原来的对话上下文里继续。
- 成员必须处于"已创建 / 运行中 / 已结算"之一。已归档的要先恢复。

### 3.2 工作模式对派任务的影响

蓝图里角色的 `contextPolicy` 决定"派给模板"时的行为：

| 模式 | `team_delegate` + 模板 时 |
| --- | --- |
| `persistent`（持久化） | 如果该模板已有一个空闲（已结算）的成员，续用它；没有就新建；有多个空闲的会报"目标不明确"，Leader 需改用成员编号 |
| `fresh_per_delegation`（一次性） | 总是新建一个成员 |

不管哪种模式，直接指定成员编号就是续用那个成员。

### 3.3 任务描述要自包含

成员拿到的只有：它的角色人设 + 这次的任务描述 + 附加材料。它**看不到** Leader 和用户的对话，也看不到其他成员的对话。所以 Leader 写任务时要把背景、要求、输出格式都写清楚。

- 任务描述最长 16384 字。
- 附加材料最长 32768 字，适合放大段原文。
- 任务摘要最长 512 字，会出现在完成通知里，方便 Leader 识别是哪个任务。

### 3.4 异步（默认）还是同步

| | 异步（不传 `async` 或传 `true`） | 同步（`async: false`） |
| --- | --- | --- |
| Leader 调用后 | 立即返回"已受理"，Leader 继续自己的事 | 一直等到成员做完，结果直接返回 |
| 成员的工作 | 在后台独立进行，Leader 这一轮结束也不影响 | 随 Leader 这一轮一起进行 |
| 拿结果 | 成员完成后系统通知 Leader，Leader 再调 `team_collect` | 直接在返回值里 |
| 适合 | 几乎所有场景，尤其是并行派多个任务 | 很短、确定不会触发审批的任务 |

**DSH 的同步派任务限制**：Leader 等待成员期间，如果成员又需要 Leader 审批，可能形成相互等待，因此默认采用异步。PilotDeck 当前只提供异步委派，Teammate 人类交互直接发给用户，见第 5.3 节。

### 3.5 异步任务的完整流程

```
Leader: team_delegate(...)  →  返回 { workStatus: "admitted", settled: false }
         ↓
成员在自己的会话里工作（可能几秒，可能几分钟）
         ↓
成员完成 → 系统记录结果（成功 / 失败 / 不可用）
         ↓
系统给 Leader 发一条通知：
  [team-work-settled requestToken=xxx]
  An asynchronous Team work unit has settled.
  instanceId: inst-xxx
  taskSummary: ...
  Use team_collect with this requestToken to read the durable result.
         ↓
Leader 空闲 → 通知触发 Leader 开始新一轮
Leader 忙碌 → 通知插入 Leader 当前这一轮
         ↓
Leader: team_collect([requestToken])  →  拿到完整结果
```

通知只带任务令牌、成员编号、任务摘要，不带结果正文。结果正文要用 `team_collect` 取。

多个任务几乎同时完成时，通常只会唤醒 Leader 一次，其余通知合并进同一轮。

## 4. 收结果：`team_collect`

- 传入一个或多个请求令牌（1 到 64 个），返回每个任务的状态。
- 状态：
  - `running`：还在做，或者系统在记录结果前崩溃了。稍后再查。
  - 终态：`succeeded`（成功，附成员的回复）、`failed`（成员报错）、`unavailable`（成员无法执行）。
- 纯读取，查多少次都不会有副作用。
- 结果持久保存，重启后仍可查。
- 如果某个令牌一直 `running`，Leader 可以用**同一个令牌**再派一次，系统会续接那个任务而不是新开一个。

重启后系统不会补发完成通知。Leader 记得自己派过哪些任务（令牌），用 `team_collect` 查即可。

## 5. 发消息：`team_send_message`

### 5.1 消息和任务的区别

| | 发消息 | 派任务 |
| --- | --- | --- |
| 成员收到后 | 把它当作一条输入，可能回复也可能只是知道了 | 开始一轮工作，产出结果 |
| 有没有结果可收 | 没有 | 有，用 `team_collect` |
| 用途 | 通知、提醒、补充信息、协调 | 交办具体工作 |

### 5.2 谁能发给谁

| 发送方 → 接收方 | 投递方式 |
| --- | --- |
| 人类 → 任何成员 | 直接送达 |
| Leader → 任何成员 | 直接送达 |
| 成员 → Leader | 直接送达 |
| 成员 → 另一个成员 | **送到 Leader 那里**，消息上标注"本意发给某某"。由 Leader 决定要不要转发、怎么转发。系统不会自动转发 |

成员之间不能直接通信，是为了让 Leader 掌握全局。当前版本没有开放"允许某成员直连"的设置入口。

### 5.3 PilotDeck 差异：人类交互请求不走消息 relay

成员在执行工具、询问用户补充信息或退出 Plan 模式时，产生的是人类交互请求，不是 `team_send_message`。请求先写入 Team 运行段的交互记录，再直接送达用户的团队交互面板：

- 权限询问对应“工具调用权限询问”板块；
- `ask_user_question` 对应“向用户提问”板块；
- `exit_plan_mode` 对应“Plan 授权执行”板块。

Leader 不会收到这些请求的普通聊天卡片，也不能代替用户处理。用户响应带有 Team、运行段、成员和请求身份，服务端校验后才回到原成员。重复响应返回已有结果，错误成员或错误聊天不能消费请求。

### 5.4 送达的含义

- 消息进入接收方的输入队列就算送达，不等接收方处理完。
- 接收方不在线（进程未驻留）会送达失败，返回明确错误，但发送意图会记入团队事件。
- 收到消息不会让接收方获得读取发送方对话历史的能力。消息里有什么，接收方就知道什么。

### 5.5 限制

- 正文最长 8192 字，主题最长 256 字。
- 发送方的协作范围（蓝图 envelope）里要有 `send-message`，否则被拒。
- 没有"异步发送"、"重试"、"已读回执"。

## 6. 进度：`team_report_progress`

### 6.1 用途

成员（或 Leader 代成员）记录一项工作的进展，让人类在"活动与进度"面板和"团队事件"里看到。

### 6.2 参数

| 参数 | 规则 |
| --- | --- |
| 成员编号 | 必填 |
| 主题 | 必填，最长 256 字，这项工作叫什么 |
| 进度 | 必填，`in-progress`（进行中）/ `completed`（已完成）/ `blocked`（受阻） |
| 摘要 | 可选，最长 512 字 |
| 最近动作 | 可选，最长 256 字 |
| 关联标识 | 可选，最长 128 字 |

### 6.3 进度不是流程引擎

记录"已完成"**不会**：自动归档成员、自动切换治理模式、自动触发下一个人、自动判定项目完成。它只是展示用的信息。

### 6.4 已知问题

成员调用这个工具时，有一定概率卡住不返回，导致成员这一轮无法结束，进而让等待它的 Leader 也卡住。目前的变通做法是在给成员的任务描述里写明"本轮不要调用 `team_report_progress`"，由 Leader 自己记录进度。

## 7. 人类在界面上做同样的事

团队视图里对成员行的操作，效果等同于 Leader 调工具，并且会以"人工"身份记入团队事件：

| 界面操作 | 等价工具 |
| --- | --- |
| "+" 创建成员实例 | `team_create_member` |
| 发送任务… / 恢复… | `team_delegate`（指定成员编号） |
| 发送跟进 | `team_follow_up` |
| 发送消息… | `team_send_message` |
| 归档 | `team_archive_member` |
| 恢复（已归档→已结算） | 仅人类可做，Leader 没有对应工具 |
| 处置 | 仅人类可做，Leader 没有对应工具 |

人类不受蓝图 envelope 限制。

## 8. 在哪里看到这些活动

| 想看什么 | 去哪 |
| --- | --- |
| 成员现在在不在干活、干到哪 | 团队视图 → 成员组（状态 + 当前动作）；活动与进度 |
| 每个成员什么时候开始、什么时候结束 | 团队视图 → 时间线 |
| 谁给谁派了什么、发了什么消息 | 团队视图 → 团队事件（筛选"成员"或"消息"） |
| 进度记录 | 团队视图 → 活动与进度；团队事件（筛选"进度"） |
| 输入框上方的一行速览 | Team 状态条："团队 · N 运行中 · M 待处理"，点开可展开成员列表和活动列表；PilotDeck 的 Teammate 人类交互改在独立面板处理 |

详见模块 5。

## 9. 推荐的 Leader 工作循环

1. `team_list_templates` 了解有哪些角色。
2. 对每个子任务 `team_delegate`（异步），写清楚自包含的任务描述。
3. 回复用户"已派出 N 个任务"，结束本轮。
4. 收到 `[team-work-settled ...]` 通知后 `team_collect` 取结果。
5. 需要成员继续改进时 `team_follow_up`。
6. 收到 `[team-control ...]` 通知时按模块 4 处理审批。
7. 全部完成后汇总给用户，必要时 `team_archive_member` 收尾。
