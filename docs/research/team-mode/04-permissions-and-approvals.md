# Team 模式功能详解 · 模块 4：权限与审批

> 本文保留 2026-10-14 的 **DSH 参考产品调研**，不是 PilotDeck 的已实现功能清单。除明确标注“PilotDeck”的段落外，文中的“当前版本”、工具、按钮和限制均指调研时的 DSH。PilotDeck 使用说明见 [docs/team-mode.md](../../team-mode.md)。
> 上级文档：[Team 模式用户功能清单](../team-mode-user-features.md)

> **PilotDeck 当前实现边界**：DSH 参考文档中的“成员请求 Leader 审批”不适用于 PilotDeck 的人类交互通道。Teammate 的工具权限询问、`ask_user_question` 和 `exit_plan_mode` 直接发送给用户，在团队交互面板处理；Leader 不接收、转发或代答。普通 Team 协调消息仍可经过 Leader relay，详见模块 3。

---

## 1. 这个模块解决什么问题

团队里有多个 AI 在自主干活，必须回答三个问题：

1. 每个 AI **能用什么**（工具、技能、外部服务、模型）
2. 每个 AI 对文件和命令的**每一次具体操作**是直接做、先问一下、还是不准做
3. "先问一下"的时候**问谁**、谁有权答、答了之后怎么执行

本模块按这三层说明，并说明人类在界面上能看到和操作什么。

---

## 2. 权限的四个等级

从低到高：

```
Teammate  <  Leader  <  人类用户  <  管理员
```

| 等级 | 谁 | 能做什么 |
| --- | --- | --- |
| Teammate | 蓝图成员模板创建的 AI | 在自己的权限内干活；遇到需要人类决定的操作就发起请求；不能批准请求，也不能改自己的权限 |
| Leader | 团队的领队 AI | 在 DSH 授权范围内处理成员控制请求；PilotDeck 不采用这条审批链，见第 5 节 |
| 人类用户 | 在界面上操作的人 | 批准所有类型的请求；给任何成员放宽或收紧权限（放宽有上限）；覆盖成员的能力配置；切换治理模式 |
| 管理员 | 更高一级的人 | **当前版本没有这个角色的操作入口**。需要管理员批准的请求会被直接拒绝 |

规则：

- 不能自己批自己。
- DSH 的请求按照所需审批等级处理；PilotDeck 的人类交互直接由用户处理，见第 5 节。
- 越往上，能批的范围越大，但都不能超过蓝图设定的上限和系统的硬性限制。

## 3. 第一层：能力配置（能用什么）

每个成员有五个能力开关：**模型、工具、技能、外部服务、权限体系**。每个开关的值来自多层叠加，从低到高：

```
蓝图团队级设置  <  治理模式  <  角色模板设置  <  Leader 的调整  <  人类的覆盖
```

然后再和系统的硬性限制求交集。规则：

- 高层的值覆盖低层。
- 人类的覆盖最高，但不能开启系统本身没有的能力，也不能突破系统硬性限制。
- 治理模式收紧时，Leader 之前做的调整会被"抑制"而不是删除，模式放宽后自动恢复。
- 哪一层都没设置的能力，默认关闭。

### 3.1 在界面上看

团队视图 → 治理 → **生效配置** 卡片，每个成员一块。每块列出几行：

| 行 | 内容 |
| --- | --- |
| model | 当前使用的模型 |
| workspace | 工作目录 |
| permissions:xxx | 各项文件/命令权限的汇总 |
| autonomy | 自主调整范围 |

每行显示：当前值、来源、状态词、以及可能的标记"已抑制"、"不可用"、"自 第 N 步 生效"。如果有系统硬性限制，额外显示"请求：xxx / 生效：yyy / 原因：zzz"。

状态词的含义：

| 状态词 | 含义 |
| --- | --- |
| Inherited | 从低层继承，没人改过 |
| Overridden | 被更高层覆盖了 |
| Suppressed | 有人设了值，但被治理模式压住了，当前不生效 |
| Unavailable | 系统里没有这个能力 |
| Denied | 能力存在，但策略禁止用 |
| Locked | 这个字段在当前阶段不能改了（如运行后的工作目录） |
| Pending next boundary | 已改，下一轮生效（如模型切换不影响正在进行的请求） |
| Degraded | 兼容性警告已确认，降级运行 |

### 3.2 在界面上改：人类覆盖

同一个卡片里，每个成员有一个覆盖编辑器：

| 控件 | 选项 |
| --- | --- |
| 能力 | model / tools / skills / mcp |
| 类型 | 允许 / 拒绝 |
| 条目 | 选"允许"时填，逗号分隔（例如模型名、工具名、服务名） |
| 查看覆盖 | 读取当前这个能力有没有人类覆盖，有则显示值，无则显示"无显式人工覆盖" |
| 设置覆盖 | 写入。选"允许"但条目为空时禁用 |
| 重置覆盖 | 撤销人类覆盖，回落到低层的值。撤销是逐条回退，不是一次清零 |

典型用法：

- 给某个成员换模型：能力选 model，类型选允许，条目填模型名，点设置覆盖。
- 临时禁掉某个成员的外部服务：能力选 mcp，类型选拒绝，点设置覆盖。
- 改完之后想还原：点重置覆盖。

模型切换对正在进行的那一轮不生效，下一轮开始才用新模型。

### 3.3 治理模式切换

团队视图 → 治理 → **策略 [当前模式]** 卡片：

- 说明文字："策略控制团队当前的运行时治理范围，不代表任务进度。"
- 点"审查"，展开每个能力的编辑行：能力名、是否"已锁定"、当前值（未设置 / 允许 [条目] / 拒绝）、以及一个下拉（none / allow / deny）加条目输入框。
- 改完点"提交"，上方预览"将提交：model, mcp"等。没有改动时提交按钮禁用。
- 已锁定的能力不能在这里改。

治理模式的候选项来自蓝图的 `policyStates`。

## 4. 第二层：文件和命令的操作权限

### 4.1 适用范围

只对蓝图里写了 `capabilities.permissions` 的角色生效。没写的角色不做这一层检查。

管的是这 7 个工具的每一次调用：

| 类别 | 工具 |
| --- | --- |
| 文件类 | 读取、读图片、写入、编辑、代码分析 |
| 命令类 | bash、PowerShell |

### 4.2 三种结果

每次调用，系统按蓝图规则判定：

| 结果 | 发生什么 |
| --- | --- |
| 允许 | 直接执行 |
| 询问 | DSH 暂停并按审批等级发起控制请求；PilotDeck 使用现有工具审批规则，直接请求用户 |
| 拒绝 | 不执行，返回错误 |

判定顺序：拒绝规则 > 询问规则 > 允许规则 > 兜底默认值（蓝图里只能是询问或拒绝）。

规则按路径匹配：精确文件、目录及其下所有内容、或整个工具。目录匹配是按真实文件系统判断的，符号链接等情况以实际位置为准。

### 4.3 命令类的特殊规则

| 角色 | 命令类工具可以配成 |
| --- | --- |
| Teammate | DSH 只能“询问”或“拒绝”，由其审批等级规则处理；PilotDeck 没有这项角色特有的命令限制 |
| Leader | 可以"允许"，但要**同时**在蓝图 `teamEnvelope.allow` 里写 `bash`（或 `pwsh`）令牌才真正自动放行；缺一个就变成"询问"，转给人类批 |

bash 和 PowerShell 分开配置，互不覆盖。

### 4.4 Leader 给成员放宽或收紧权限

Leader 有两个工具：`team_grant_permission`（追加规则）和 `team_revoke_permission`（撤销规则）。

| 变更方向 | 处理 |
| --- | --- |
| 收紧（如把允许改成拒绝） | 立即生效，不需要任何审批 |
| 放宽（如把询问改成允许） | 必须落在蓝图 `permissionMutationEnvelope` 规定的范围内，超出直接拒绝（不会变成待审批） |

几个细节：

- 撤销也可能是"放宽"：撤掉一条拒绝规则后，下面更宽松的规则冒出来了，这种撤销同样受上限约束。
- 一次传多条规则时，只要有一条超限，整批都不执行。
- 规则集和现有完全相同时不做任何事，返回 `changed: false`。
- 变更会通知正在运行的成员（一条简短提示，告知权限已更新），空闲或未驻留的成员不会被唤醒。
- 成员自己不能调这两个工具。

**一个要避开的坑**：把某个命令类规则从"允许"收紧到"询问"是可以做的，但做完之后这条命令就永远执行不了了，因为能批准它的是"管理员"级别，而当前版本没有管理员。界面上也没有解开的入口。要限制成员执行命令，用"拒绝"而不是"询问"。

### 4.5 人类放宽权限的上限

人类通过远程接口（当前界面没有直接的表单）给成员放宽权限时，上限是蓝图的 `teamHardEnvelope`。超出需要管理员，当前版本等于拒绝。

### 4.6 在界面上看

团队视图 → 治理 → **权限管理** 子卡片（在"治理介入"面板内）：

| 内容 | 说明 |
| --- | --- |
| 身份行 | 团队标识、成员标识（团队级时为空）、权限代数（没有变更记录时显示"蓝图默认"）、来源 |
| 规则列表 | 每条一行：`类别 · 匹配方式 路径 · 效果`。目录规则就显示目录路径，不展开成文件树。空列表显示"无生效规则。" |
| 诊断 | 蓝图两个上限字段的一致性检查结果等 |

这个卡片是**只读**的。人类在界面上不能直接编辑权限规则。

## 5. PilotDeck 差异：面向人类的交互请求

### 5.1 请求怎么产生

| 场景 | 记录类型 | 用户入口 |
| --- | --- | --- |
| Teammate 的文件/命令操作命中“询问” | `tool_permission` | 团队交互 → 工具调用权限询问 |
| Teammate 调用 `ask_user_question` | `user_question` | 团队交互 → 向用户提问 |
| Teammate 调用 `exit_plan_mode` | `plan_approval` | 团队交互 → Plan 授权执行 |
| Leader 自己需要人类确认 | 普通会话交互 | Leader 主聊天现有交互卡片 |

Teammate 请求先原子写入 Team 运行段的 interaction ledger，再发出专用事件。Leader 不收到这些请求的普通聊天卡片，也不触发 Leader 自动续答、`team_collect` 或 relay。发起成员的回合暂停，等待用户处理。

### 5.2 团队交互面板

入口与“团队详情”并列，按钮显示未处理数量。面板只列 Teammate 卡片；成员卡片不重复显示模型、工作区、工具、技能或 MCP，这些信息在团队详情中查看。

每个 Teammate 卡片有三个可展开区：

- **工具调用权限询问**：点击通知行后复用普通会话权限卡片；
- **向用户提问**：点击后复用问题卡片，支持选项和回答；
- **Plan 授权执行**：点击后显示计划详情，并提供批准或拒绝执行。

处理完成的记录继续保留，显示允许/拒绝、已回答/已取消、已批准/已拒绝、已过期或失败。刷新和重连从 ledger 恢复，不能把 pending 记录降级成普通聊天或丢失。

### 5.3 响应路由和幂等

用户响应带有 Team、`activationId`、`stopVersion`、Teammate、交互 ID 和原始 `requestId`。服务端校验全部归属后，才向原成员的内部等待句柄返回结果。错误聊天、错误成员、旧代次和错误 Team 都被拒绝，原记录保持 pending；同一请求重复响应只返回已有结果，不产生第二次工具调用。

停止或 Gateway 重启后仍为 pending 的请求分别标记为取消或过期，保留历史但不可继续执行。

### 5.4 Leader 自身的交互

Leader 的权限询问、用户问题和 Plan 授权继续使用普通会话的底部交互卡片。Leader 可以使用团队工具协调成员，但不能通过这些工具代替用户处理 Teammate 的人类交互请求。

## 6. 兼容性与环境要求

蓝图里声明的环境要求（`requirements`），在团队创建后仍会持续核对。

团队视图 → 治理 → **兼容性** 卡片：

| 元素 | 内容 |
| --- | --- |
| 状态徽章 | ✓ 兼容 / ⚠ 降级（有警告但已确认）/ ⚠ 需要处理（有新警告）/ ✕ 结构性错误 |
| 计数 | `N 项警告 · N 项致命 · N 项已确认`，代数，最后探测时间 |
| 审查 | 读取最新结果，展开显示各项计数 |
| 重新检查 | 重新核对环境。提示："重新检查会生成新的兼容性代数；旧的确认不会自动覆盖新代数。" |

环境变化（例如外部服务断了）会让团队进入"需要处理"状态：已经在跑的任务继续跑完，但新任务不再受理，直到问题修复后重新检查通过。

创建后新出现的警告**无法在界面上逐项确认**（按钮永久禁用），只能修复环境后重新检查。

## 7. 治理警告

蓝图里 `permissionMutationEnvelope` 和 `teamHardEnvelope` 两个上限字段如果自相矛盾或无法判定，系统会在以下时机产生治理警告：

- 创建团队时：团队建好但 Leader 不启动，等人类确认后才启动。
- 运行中触碰到相关边界时：团队继续运行，警告出现在"治理介入"面板。

警告在"治理介入"面板里以"warning"类型显示，带"确认"按钮。确认只是表示"我看到了"，**不改变任何权限**。同一个警告反复出现只会更新次数和时间，不会堆成多条。

## 8. DSH 参考：审批记录完整性提示

如果人类交互记录因为某种原因无法解析，DSH 的治理面板顶部会出现一条固定的提示条："交互账本存在无法解析的损坏记录（仅提示，不改变执行语义）"，逐条列出序号和能否归属到某个成员。

- 提示条不能关闭。
- 损坏的记录在 DSH 审批详情里标为"损坏 · 不可处理"，不能继续执行。
- 其他操作不受影响。
- 完整性检查本身失败时显示："审批记录完整性检查暂不可用，无法确认是否存在损坏记录（仅提示，不改变执行语义）— 请刷新重试"。

## 9. DSH 参考与 PilotDeck 差异：谁能改什么

| 想做的事 | Teammate | Leader | 人类 |
| --- | --- | --- | --- |
| 发起审批请求 | 自动产生 | 可以 | 不需要 |
| PilotDeck：处理 Teammate 人类交互请求 | 否 | 否 | 是（团队交互面板） |
| PilotDeck：处理 Leader 自身交互请求 | 否 | 否（由普通会话卡片处理） | 是 |
| DSH：收紧某成员的文件/命令权限 | 否 | 是，立即生效 | 是 |
| DSH：放宽某成员的文件/命令权限 | 否 | 是，受 `permissionMutationEnvelope` 限制 | 是，受 `teamHardEnvelope` 限制 |
| DSH：运行时改某成员的模型/工具/技能/外部服务 | 否 | 否 | 是，治理面板"设置覆盖" |
| 切换治理模式 | 否 | 否 | 是，治理面板"策略" |
| 重新检查兼容性 | 否 | 否 | 是 |
| 确认治理警告 | 否 | 否 | 是 |

PilotDeck 没有移植本篇 DSH 的治理模式、多层能力覆盖、`team_grant_permission` / `team_revoke_permission`、权限 envelope 或管理员审批。角色能力在配置库设置，运行时使用冻结快照；这些参考功能不属于本次交互面板的实现与验收。
