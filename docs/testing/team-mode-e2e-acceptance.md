## 1. 执行和判定规则

- 每个 case 的“首次覆盖的功能”只列之前未列过的功能；后续操作可能再次用到它们，但不重复计入覆盖。
- **真实使用**：真人操作真实 Web 页面，经过真实 Gateway、存储和实际配置的模型。既看流程，也看任务交付物是否合理。
- **辅助观察**：读取测试环境的请求记录、Team 记录和文件，或回放一次已捕获请求。界面没输出不能证明零模型调用；模型说“已完成”不能证明任务完成。
- **受控故障**：在独立测试环境中延迟请求、丢弃响应、断开浏览器、终止服务或替换模型输出。它验证异常分支，不能代替真实模型的协作效果验收。
- 每条功能分别记录：`通过 / 失败 / 部分覆盖 / 未触发 / 环境阻塞 / 未执行`。一个条目只完成部分分支时记“部分覆盖”；已出现的明确失败不能被其他成功分支抵消。允许更明确地重试，但保留失败或未触发的原始记录。

### 配置保存与生效边界

**配置库只保留每个 Leader、Teammate 和 Team ID 的最新配置。Team 按成员 ID 静默沿用最新角色配置；正在执行的整队保持本轮快照，直到全队空闲，或 Abort 清理完成 / Gateway 重启后，再在下一次工作中静默使用最新配置。**

- 保存覆盖同一 ID 的当前配置，不生成配置修订号、历史数组或可供回滚的旧配置。角色编辑不要求再次保存引用它的 Team，也没有“有更新 / 查看变化 / 采用最新配置”流程。查看页面时允许刷新取得最新数据；这不等于手动采用配置。
- 两个编辑者使用各自的新请求 token 保存同一 ID 时，以服务端最后成功写入的完整配置为准，不要求修订冲突检查。相同 token 改参数仍属请求冲突；相同请求的重试不能重复创建对象，也不能把后来保存的配置回退。
- “全队空闲”不能仅由 Leader 已给出回答或聊天窗口仍打开来推断。需要确认 Leader 和全部 Teammate 均无活跃 Agent Loop，也没有有效排队消息或待发送程序通知。仍在审批、提问的执行不算空闲。空闲后才发生的配置编辑，也必须在下一次实际工作中生效。
- Abort / Gateway 重启后的配置更新不重新启动旧任务，也不恢复旧 pending 消息。下一次明确的新人工请求使用最新配置；只刷新浏览器、断开 WebSocket 或重启 Web bridge，不等于 Gateway 重启或全队执行终止。
- 删除用于配置清理，没有归档筛选和恢复入口。被任一 Team 引用的角色不能删除；删除配置不等于停止执行或删除运行历史。旧 activation 的记录与 transcript 属于运行证据，不是配置库的历史版本。
- 文件格式 `state.version`、运行代次 `stopVersion` 和成员只读流的 `revision` 分别用于解析、停止隔离和增量排序，继续保留；它们不是角色或 Team 的配置版本号。

### 停止与重启的判定边界

**Abort 或 Gateway 重启后，旧运行中尚未应用的消息必须失效。无论接收者是 Leader 还是 Teammate，都不能由这些旧消息自动启动新回合，也不能在后续新回合中补投递。用户明确发送新请求后，当前运行产生的新消息可以正常激活接收者。**

- pending 指可靠保存但尚未实际发送到模型请求的消息，包括排队与准备中的消息。只有最终请求体含正文且已调用实际 SDK/网络入口，才算消费；`input_accepted`、`steer_applied`、邮箱接纳和模型口头确认均不能单独证明。发送记录不表示模型服务端确认收到或理解。发送过程中崩溃而不能确认的记录为“发送情况不确定”，不自动重发、不宣称可撤回。
- 每个分支分两个观察窗口：先在没有新人工输入时检查旧消息不能自动唤醒；再明确发送新请求、产生当前代次的新消息，检查旧消息仍未补投递而新消息可以正常应用。Abort/Gateway 重启 × 接收者 Leader/Teammate 四种组合分别留证，未形成真实 pending 前态的分支不能算通过。
- 用 `activationId + stopVersion + message.id/teamEventIds + turnId + requestId/attemptId` 关联旧消息、最终请求体、发送记录及接收轮次；程序通知和删除反馈也是消息。模型新一轮生成同文消息会得到新身份，不能按正文相同认定旧消息被重投。逻辑请求重试可以有多个实际发送 attempt，但注入只展示一次。
- 新回合中模型忽略当前请求、重发旧内容或重新调用旧命令，单列为“模型行为观察”，保留原 prompt、调用和真实效果；它不单独判定消息失效或停止/重启机制失败，也不保证新请求的任务交付成功。只有追踪到旧消息被自动启动/补投递、旧请求被重新接纳等程序行为，才判对应生命周期断言失败。
- transcript 的过滤、工具调用/结果配对补齐属于请求格式恢复行为；本组用例不预设必须采用某种恢复形式，也不凭恢复形式或模型表现直接认定上下文管理缺陷。

以下配置在 Case 01 中通过界面建立。其余 case 默认使用当前保存的配置；需要改模型、权限或能力时，Fork 一个标有 case 编号的临时变体。仅 Fork Team 仍共享原成员 ID；需要独立修改角色时，还须 Fork 对应角色并在临时 Team 中替换，避免影响其他用例。

### 2.3 如何留证

每个 case 保存一份简短记录：代码提交/构建、环境、模型、角色和 Team ID、当前配置内容及 `updatedAt`、操作时间、会话 URL、输入原文、实际结果、逐条功能结论及证据位置。配置变化的前后对照由测试者另存为证据，不要求产品保留历史版本。

- 用户可见证据：录屏/截图、Leader 最终回答、团队详情、实际生成文件、命令结果。
- 结构化证据：通过实际页面请求或 `team_command` 的 `library`、`runtime_get` 响应分别查看最新配置、执行轮次、消息和实际发送记录；分页需读完对应 cursor。Team 的 `config.leader` / `config.teammates` 只含 `{ id }`；保存不提交 `expectedRevision`。核对当前配置为单条对象而非修订数组，不带 `revision`、`archived` 或 `forkedFrom`。Web 入口是 `POST /api/team-library`，沿用当前登录凭据；报告不得附 Cookie、Token 或模型密钥。
- 配置生效证据：保存编辑前后 `library`、`runtime_get`、实际模型请求和工具效果，并标明最后一个 Agent Loop 结束、消息/通知处理完、Abort 清理完成或 Gateway 重启的时间。仅看到配置库已更新、面板文字变化或模型自述，不能证明执行已采用最新配置。
- 人类交互保留完整 owner：`sessionKey + activationId + stopVersion + participantId + interactionId + requestId + kind`，以及请求快照、状态、响应和处理时间。Gateway 使用 `team_interaction_respond` / `team_participant_messages`；Web action 分别为 `runtime_interaction_respond` / `runtime_participant_messages`。记录 `runtime_get` 的返回及实际分页 cursor，不能只以 WebSocket 通知证明落盘。
- 区分专用 `team-interaction`、`team-interaction-updated`、`team-participant-message` 帧与 Leader 的普通权限帧。只读流记录 owner、消息/turn ID、`streamEpoch`、流式 `revision`、订阅/退订和刷新前后内容；该字段不属于已移除的配置版本机制。受控重放旧帧的结果不能冒充真实网络重连。
- `activation.id` 表示这一次进入 Team 模式的运行段；`stopVersion` 表示停止隔离代次。`message.id` 标识消息，`turnId` 标识一次执行，`requestId` 标识逻辑模型请求，`attemptId` 标识一次实际发送。旧 `work.id` 仅作为历史读取，不再生成新任务。测试者记录程序生成的身份。
- 请求回放保留捕获时的完整身份：`submit_turn`/steer/Abort 的 `teamActivationId + teamStopVersion`，以及 `runtime_stop` 的 `activationId + stopVersion`。测试驱动不能先读最新代次再替换旧请求，否则测不到过期请求拒绝；新人工请求才读取当前身份并使用新 token。
- 需要证明接纳次数时，检查主聊天 transcript 的 `accepted_input`；需要证明模型、工具实际运行次数时，另看相应调用记录。两者不是同一个计数。
- 运行中消息区分“已保存”“准备发送”“实际发送模型请求”。保存 `teamEventIds`、轮次、request/attempt、最终请求体及相应 transcript；两种方向与成员直连均以实际发送为消费边界。空闲时启动一轮、忙时当前轮注入，不将准备阶段标成已注入。
- Case 19、20 额外记录每条旧 pending 消息的接收角色、消息/事件 ID、原代次、入队/应用时间，以及停止/重启后的失效状态；关联后来每个接收回合的触发来源。记录无新输入窗口的起止时间与延迟放行点，再记录明确新输入及新消息身份；总调用数、正文相同或副作用计数变化均不能代替来源核对。
- 内部成员上下文在 `${PILOT_HOME}/team-runtime/contexts/`，运行记录在 `${PILOT_HOME}/team-runtime/state.json`，配置在 `${PILOT_HOME}/team-library/state.json`。只在测试副本中直接修改它们。

## 3. 用例

### Case 01：从零配置一支可复用的发布评审团队

**方式：** 真实使用＋辅助观察。先记录聊天文件数量、模型请求计数和 MCP 连接计数。

**操作与期望：**

1. 从侧栏“团队”进入 `Leaders`、`Teammates`，按基准先建立发布负责人和代码审查员，测试员留到步骤 4 创建。先试空显示名称或空系统提示词，再补齐保存；前者不能保存。
2. 两类角色都填写描述并选择具体模型；模型支持时选择推理强度、速度。试选固定 P2，再改回继承。切换“能力清单来源”，确认它不改变工作区模式。用临时角色依次保存、读回“需要时请求审批”和“跳过权限提示”，基准角色最终保持“需要时请求审批”；Plan 通过实际工具进入，另按 Case 14 验证。
3. 勾选工具、技能和 MCP 中各一个测试条目，确认没有 Optional 配置。两类角色分别检查：勾选 plan 工具组合时自动选中并锁定 `todo_write`；取消组合后 `todo_write` 保持选中且可以取消，也可单独勾选并保存。最终恢复基准能力。
4. 新建 Team，先试缺 Leader、没有 Teammate，确认不能保存。填写显示名称、描述、团队说明和默认工作区，选择一位 Leader；在 Team 编辑器内新建测试员，保存后回到原 Team 草稿且自动选中。
5. 保存并重新打开详情，核对字段、系统 ID 和最新配置；页面及配置响应不显示 v1/v2 等配置版本。确认配置操作没有创建聊天或调用模型，保存能力选择也没有启动 MCP 业务工具。
6. 辅助回放非法保存请求：重复 Teammate、错误角色引用、不存在的角色 ID、伪造新对象 ID、未知配置字段，以及旧 `revision` / `expectedRevision` 字段。记录拒绝结果，确认没有多出配置；合法 Team 引用和 Fork source 只提交 `{ id }`。

**首次覆盖的功能：**

- [ ] F001：可从零创建 Leader 和 Teammate，名称/系统提示必填，字段校验有效，ID 由服务端生成。
- [ ] F002：模型及可支持的参数、工作区继承/固定、能力允许列表能够保存，plan 工具强制依赖 todo_write；能力清单来源仅影响展示。
- [ ] F003：Team 可组合一位 Leader 和至少一位不重复的 Teammate，按 ID 保存成员、说明和项目引用，拒绝不存在的成员、错误角色及已移除的版本字段等非法输入。
- [ ] F004：Team 编辑过程中可创建角色并返回原草稿，配置保存与聊天执行分离。

### Case 02：编辑到一半、保存失败和多人同时编辑

**方式：** 真实使用＋受控网络故障。使用临时配置，不改基准 Team。

**操作与期望：**

1. 分别填写一半角色草稿和 Team 草稿，不关闭编辑器，直接刷新浏览器；输入应恢复。随后点“放弃草稿”，刷新后不应再恢复。当前实现中编辑器 X/Esc 也会放弃该草稿。
2. 让能力清单请求失败，已有勾选仍保留，不能误以为空列表后覆盖配置；恢复请求并点重试。
3. 用代理或浏览器自动化让一次保存请求成功到达服务端，但丢弃响应。保存编辑器保留失败状态，字段冻结；点“重试”仍对应同一次保存和同一对象 ID，不新增副本。对一次 Fork 确认请求重复同样实验，保持名字不变再次点“复制并修改（Fork）”，副本只创建一次；Fork 确认窗口并不使用保存编辑器的“重试/新尝试”按钮。
4. 失败后需要改内容时，点击“作为新尝试继续编辑”。回放旧 token＋修改后参数应报冲突；新尝试可以保存。
5. 两个标签页打开同一角色，分别改成带唯一标记的完整配置，各使用新 token：A 先保存，B 后保存，均允许成功；重新读取和重启后只得到 B 的配置，不报告修订冲突、不合并两份字段。对 Team 重复此分支。最后原样回放 A 的旧保存请求，不能回退 B 的持久配置，也不能新增对象。

**首次覆盖的功能：**

- [ ] F005：本机未关闭草稿可恢复，明确放弃后清除。
- [ ] F006：能力目录加载失败保留选择并可重试。
- [ ] F007：配置保存和 Fork 操作的重试 token 保持幂等，改参数须新尝试；响应丢失不重复创建。
- [ ] F008：同一 ID 以最后一次成功保存为准，只保留最新配置；角色和 Team 均无修订冲突流程，旧请求重试不回退后续保存。

### Case 03：覆盖更新角色，Team 按 ID 静默使用最新配置

### Case 13：成员之间并行，同一成员内部串行

**方式：** 真实使用＋可控延迟工具。提示模型“同时做”不足以证明并行。

**操作与期望：**

1. 临时为审查员、测试员授权 `bash`，在 P1 运行现成的 `python3 qa_gate.py <任务标签>`，每轮使用新标签。脚本在 `out/gates/` 写入 `<任务标签>.started` 后等待放行，结束后写入 `.finished`；测试者在 P1 执行 `touch out/gates/<任务标签>.release` 放行。工具超时须覆盖计划等待时长（脚本最多等待 180 秒）；若命令转入后台，仅有 `.started` 不能证明成员执行仍被占用。
2. Leader 发送审查员 A1、测试员 B1 两条工作要求；等两者进入延迟工具后，再给审查员追加 A2。读取轮次及 `.started` 时间证明 A1/B1 重叠，A2 尚未形成第二个审查员 Loop。不能把工具调用数组顺序当作实际发送顺序。
3. 先释放 B1，其正式结果可先落盘；A1 仍运行。再释放 A1，让审查员当前轮下一模型请求消费 A2；若 A1 在下一边界前已结束，A2 才由后续轮消费。两条要求不对应两个独立任务记录。
4. 分别在 Leader 空闲、LLM 请求中、工具执行中及结束前边界释放成员结果。程序通知不带结果正文，忙时进入下一请求、闲时启动一轮；保存最终请求体及 request/attempt 发送记录。通知入队和 `steer_applied` 不提前作为已消费证据。
5. 在 Teammate 执行中送达随机标记消息，确认实际发送后当前 turn 显示分隔线及注入正文，不另开 Loop。准备阶段的消息仍为准备发送；空闲收信以包含发送者的 user message 展示整批消息。Leader 空闲收信则在上一条最终回答后显示浅灰线，流式输出在其下，正文不伪装成人类输入；刷新/重连后的分组一致。
6. 用普通聊天对照：两个相同工作区的会话均能发出首次模型请求；Leader、Teammate 共享目录也不因整轮工作区租约串行等待。比较执行前后旧检查点目录，不新增自动快照或备份；已有备份保持原样。本分支须直接使用共享 P1，分别固定 P1/P2 的成功不能代替它。
7. 让 A1 模型调用发生明确不可恢复错误，B1 保持正常。A1 轮次保存正式错误和结束原因，B1 可正常结束；Leader 收到固定结束通知后查询 A1 错误，不能将全队汇总为成功。另分别验证正常结束、步数上限及准备环境失败，不能把工具命令退出非零直接等同 Agent Loop 异常。

可复用本例中仍在运行的成员检验 Case 14A 的实时只读聊天：记录历史快照之后实际收到的增量和最终落盘结果。只看已完成 transcript 不算流式覆盖，也不重复计入 F038/F039。

**首次覆盖的功能：**

- [ ] F038：不同成员可并行执行，同一成员实际执行严格串行；同目录的普通会话及 Team 角色不再被整轮检查点锁挡住首次模型请求，执行不新增自动检查点。

### Case 14：Teammate 直接请求人类处理

**方式：** 真实使用＋错误会话响应回放。先用隔离环境的现有权限规则保证测试操作确实要求审批；仅使用测试目录中的无害写入或命令。

**操作与期望：**

3. 在两个独立 root session 中同时制造待处理权限：A 是 Team Teammate 的 `write_file`，B 是另一 Team 的 Leader 普通权限请求；尽量使用不同执行目录和唯一文件内容。先在 A 打开通知行，核对弹窗标题包含 A 的 Teammate display name，并核对文件路径、参数内容、`sessionKey`、`participantId`、`activationId` 和 `requestId` 均属于 A，不能只凭“有一张权限卡”判断。再切换到 B，核对 B 页面显示 B Leader 的普通权限卡，路径和内容属于 B，A 的成员名和参数不得残留；若弹窗阻止侧栏第一次切换，先记录关闭弹窗再切换的实际行为，不把该 UI 操作限制误判为串台。返回 A 后重新打开同一行并拒绝 A；在点击前后读取 B 的运行快照，证明 B 仍为 pending，A 变为 `denied` 且只有 A 的成员 work 收到 `permission_denied`。最后单独处理 B 清理环境。该步骤同时验证“打开 A 后看到的确实是 A 卡片”和“跨 session 决定不会落到另一张卡片”。记录两个 session 的执行目录；同目录与不同目录应作为两个独立子分支，不能用其中一个替代另一个。
4. 捕获一条真实 pending 请求，逐项替换 root session、成员、`activationId`、`stopVersion`、`interactionId`、`requestId` 或 `kind` 后回放；每次拒绝后重新读取 ledger，原请求仍 pending。另尝试从普通聊天权限响应入口回答成员请求，不得消费它。最后用正确 Team 卡片回答才解除原成员等待。测试相同响应并发提交及服务端成功但响应丢失后的重试；只返回已有结果，原工具最多执行一次。仅前端禁用按钮不算服务端去重证据。
5. 要求 Teammate 调用 `ask_user_question` 询问发布环境，包含单选和多选问题；问题只出现在“向用户提问”区域。刷新页面和真正断开再连接 WebSocket 后仍能看到；分别回答和取消，检查原成员收到准确选项、补充说明或取消结果，历史保留。关闭弹窗或按 Esc 仅关闭查看，不等于回答或取消；区分它与 Case 12 的成员间等待信息。

7. 分轮准备三类真实 pending 请求后分别停止 Team 或重启 Gateway，检查仍 pending 的交互分别变为已取消或已过期，历史快照保留但不可再次执行。这里记录 Case 19、20 的交互子分支，F060/F063 不参与。另在普通聊天和 Team Leader 各验证权限、问题、Plan 仍沿用普通底部卡片，响应只影响原执行。回答后等待工具结束，再刷新并展开历史卡；卡片应显示真实答案，不能把已回答显示为已跳过。

**首次覆盖的功能：**

- [ ] F041：Teammate 工具权限询问直接进入团队交互面板，Leader 主聊天无卡片；允许/拒绝真实影响工具执行，已处理记录保留。

### Case 18：首次发送、响应丢失和重复提交

**方式：** 真实页面＋请求回放/断网。先选好 Team，发送只读取测试数据的任务，记录首次 root、选择 token 和输入 runId。

- F063（非缺陷，本期排除）：保留编号追溯历史结论，不纳入 Team 人类交互面板修复与验收。

### Case 21：统一消息不受累计续轮限制，实际发送记录可核对

**方式：** 受控端到端。需要可控的成员完成节奏与通知接纳响应；不依赖真实模型自由聊天恰好产生足够轮次。

**操作与期望：**

1. 连续制造 25 次以上空闲接收消息或固定结束通知，分别等上一轮退出再释放下一批。全部按同一规则启动，无第 24 次累计暂停；单轮步数上限仍保留，Abort 可停止整个团队。
2. 正式结果写入后、程序通知投递前暂停并读回：结果已保存，通知仅含成员、轮次和结束原因及查询方式，不夹带结果正文。准备失败、异常和步数上限均通知；Abort/重启及全部撤回的空执行不发可唤醒旧通知。
3. 在实际请求入口前后分别注入故障。入口前消息仍未消费；入口已调用但响应未返回时不可删除，不等待响应才裁决删除。实际请求体和发送记录中的 message IDs 必须一致；不能以 transcript 接纳回执替代。
4. 触发网络 retry/fallback，核对每次实际 attempt 的编号、接收者、轮次、消息编号和时间；逻辑重试正文一致，不重复插入正式注入记录。无法确认是否发送的 crash 分支不得自动补发。新增消息进入下一批，不能改变前一请求重试的正文。

**首次覆盖的功能：**

- [ ] F064：取消累计自动续轮限制，保留单轮步数上限和整队 Abort；每个成员最多一个 Loop。
- [ ] F065：正式结果先保存再固定通知，消费以最终请求体及实际发送入口为准；每次实际 attempt 可追溯，删除竞争和重试不造成假消费或重投。

### Case 22：Team 数据缺失或损坏时明确报错

**方式：** 受控故障。使用 `fault-home`，先完成一次 Case 09 取得真实记录；停止服务、保留原文件后逐项注入故障，每个分支结束即还原，不混合损坏条件。

**操作与期望：**

1. 选一条有 Team 输入记录的聊天，暂时移走 runtime journal，启动后直接打开原 URL。Team 身份读取、发送、切换及历史修改应明确报错，不能把它当普通聊天运行。
2. 还原后单独损坏 runtime journal 的 JSON 或校验和，再尝试读取；保持报错，不覆盖原损坏证据。
3. 分别对配置库文件、活跃 Team 的主聊天 transcript 做对应损坏分支；配置不可读时不能当空配置库重建，活跃 Team 续聊检测到 transcript 解析错误时应拒绝提交。只读历史和退出 Team 后的普通续聊尚未统一执行该诊断，见已知问题，不宣称所有入口都能阻断。
4. 另只模拟身份查询网络失败：界面保留错误，阻止发送/切换；恢复服务后点击重试，应重新恢复正确身份。每个磁盘故障分支还原文件后也能读回原记录。

**首次覆盖的功能：**

- [ ] F066：Team 身份/配置数据损坏不静默降级或覆盖原数据；活跃 Team 续聊检测到聊天记录解析错误时拒绝提交。
- [ ] F067：身份加载错误有可恢复的界面状态和重试入口，恢复成功后才重新开放操作。

### Case 23：保护 Team 历史与被引用项目

**方式：** 真实使用＋后端请求回放。项目操作限定为已备好的 P1、P2 和 `deletion-target`。

**操作与期望：**

1. 在有 Team 执行历史的聊天试用普通分叉、删除、重做最后一轮、改写历史；前端不可用或给出错误。回放对应接口仍须拒绝，不能只测菜单隐藏。
2. 在 Team 与普通聊天分别回放所有旧 `manage_checkpoints`/checkpoint HTTP 操作（含 list/diff、恢复、撤销及旧 Git 操作），均返回 `CHECKPOINTS_REMOVED`；HTTP 为 410，不读取备份、不恢复文件。原检查点 UI 不再出现，旧备份文件字节保持。这里被移除的是旧检查点接口承载的 Git 操作；Git 查看与操作走独立 `repository_operation`/现有 Git 路由，应仍正常。
3. 在普通聊天对照文件产物卡片、预览、下载、引用以及普通 Fork/编辑最后消息；历史中已有恢复边界仍只读重放，不重新显示以前隐藏的内容。
4. 退出 Team 改为普通模式后重试，历史保护仍存在。正常重命名、聊天和明确继续工作仍可用。
5. 试删被当前角色固定工作区、当前 Team 默认项目/成员工作区或既有运行快照引用的项目，包含强制删除请求，应阻断。修改配置解除项目引用或按 Case 05 删除临时 Team / 无引用角色后，重新检查：当前配置不再引用的旧项目不因已移除的配置修订而永久受保护；但只要既有 activation 仍引用它，即使配置已删除或更新，项目保护仍有效。用从未创建运行记录的临时配置另做解除引用后可删的对照。
6. 在项目关联检查不可达或数据损坏时发删除请求，不能把检查失败当作“无引用”。用未被引用的 `deletion-target` 做正常删除对照。

**首次覆盖的功能：**

- [ ] F068：Team 历史修改保护继续有效；检查点及回滚 UI/接口全局撤销且旧备份保留，独立 Git、文件产物、普通聊天编辑/Fork 和旧恢复边界只读重放不受影响。
- [ ] F069：项目删除检查配置及冻结运行引用，强制删除和检查失败都不能绕过；无引用项目仍按普通流程处理。

### Case 24：手机、主题、语言与长内容下仍能完成操作

**方式：** 真实页面。覆盖桌面浅色、桌面深色、手机约 390px 宽浅色/深色，至少中文和英文各走一次关键路径。

**操作与期望：**

1. 侧栏展开和收起状态分别进入配置库；完成一次角色编辑、选择 Team、打开团队详情，不存在必须靠桌面宽度才能触达的按钮。
2. 使用长 Team/成员名称、长系统提示和长兼容性错误，查看菜单、弹窗、卡片及消息。内容可换行/滚动，确认、取消、重试按钮可操作，不横向溢出遮挡。
3. 用键盘打开对话框、Tab/Shift+Tab、Esc 关闭，检查焦点停留和返回；留意配置编辑器关闭会放弃草稿，不能误以为已保存。
4. 切换语言，核对运行状态、兼容性结果、停止/重试和历史入口；错误可含服务端原文，但界面不能因长错误损坏布局。
5. 对团队交互入口、三类弹窗、处理历史和成员只读聊天执行 Case 14A 步骤 7 的视口/主题/语言/键盘检查。记录具体组合与截图；新界面结果归 F079，原配置库和菜单结果仍归本例 F070/F071，不能用其中一种代替另一种。

**首次覆盖的功能：**

- [ ] F070：配置和运行入口适配收起侧栏、手机与深浅主题，长内容和错误不破坏操作布局。
- [ ] F071：关键交互具有中英文文案及可用的键盘焦点/关闭行为。

### Case 25：旧版本化配置收敛为最新值，过渡逻辑不复活

**方式：** 升级环境端到端＋存储字节核对。检查并复制已有 `legacy-home`；不足时在测试副本补充合法校验和的旧格式样本，涵盖格式 1/2、多个历史修订、归档标记、固定旧角色修订的 Team、配置操作收据和旧启动收据。另建原子写入失败分支，旧 `legacy-backup-failure-home` 的备份障碍不再代表当前迁移路径。这些是测试样本，不能据此写“已验证线上升级”。

**操作与期望：**

1. 启动当前服务，只打开配置库读取，原文件字节保持不变。每个 ID 只展示旧数组中的最后一条配置，去除配置 `revision`、`archived`、`forkedFrom`；原归档对象作为普通当前配置展示，不提供恢复入口。即使旧 Team 曾固定早期角色修订，`library` / 新预检也应按成员 ID 解析最新角色。
2. 通过 UI 保存一次合法配置，原子写入单条最新对象和 ID-only 引用；重启后读回一致，不再保留历史修订数组或版本链。旧文件中的成员嵌入内容和请求去重记录也须检查，不能经这些位置保留可用的旧配置历史。`state.version` 只作文件格式标识，不是产品配置修订号；不再要求迁移生成历史备份。
3. 在独立副本对临时写入/原子替换制造可确认的失败，保存应报错，原有效文件字节不变；解除故障后可重试并读回最新配置。损坏 JSON/校验和另按 Case 22 验证，不与写入失败混合。
4. 对迁移后的新保存/Fork 执行 Case 02 的幂等与旧 token 改参数检查。旧收据不能复活已删除对象或把配置回退为历史值；旧 API 中的配置 `revision` / `expectedRevision`、归档 action 均按 Case 01 / 05 拒绝，不要求旧版本请求原样继续保存。
5. 旧启动收据、独立成员聊天绑定不能重新创建成员聊天；旧 `start`、`probe`、`conversation_get` 命令被拒绝。当前 `runtime_probe` 等命令与它们不同。runtime 升级到新格式保留旧 work/message/transcript，只恢复 transcript 能证明的稳定轮次；旧 delivered 标为消费未知，不追认为已发模型，旧 pending 不恢复。

**首次覆盖的功能：**

- [ ] F072：旧配置读取不改写，按 ID 选最新值并移除配置版本/归档字段；首次成功写入后只保留当前配置，原子写入失败保护原数据，请求重试不回退或复活配置。
- [ ] F073：已移除的过渡启动命令和成员聊天绑定不参与当前执行，不因升级恢复独立成员聊天。

## 4. 当前边界与已知问题

执行时用本节解释范围，不能将以下未支持功能计为漏测或通过：

- 当前没有可输入的独立成员聊天、动态招募/删除运行成员、同角色多实例、Leader 自动审批、分层权限治理、在线蓝图编辑或甘特图。成员直连默认允许，不需要开关；Teammate 只读聊天展示 transcript 和流式输出。
- 配置管理不提供版本选择、变化比较、显式采用、历史回滚或归档恢复。Fork 是创建新 ID 的独立配置；Team Fork 仍共享成员 ID。Case 03 / 16 检查最新配置与生效边界，不能把“没有这些入口”记为缺失功能。
- 两个通信工具分别发送和查询，没有任务登记、引用原消息、Leader relay、等待信息或结果 collect。忙时进入当前执行下一请求，闲时整批启动一轮；面板刷新只读状态。已发出的模型请求不能改写。
- 能力设置约束工具接口、技能入口和 MCP 接入，不能代替操作系统沙箱。共享项目文件不天然隔离；禁止工具桥接口也不保证其他获授权执行接口无法操作同一文件。
- 服务仍运行时的浏览器刷新可恢复审批；Abort/服务重启使旧消息、通知、审批回复及未完成任务失效。共享目录没有整轮检查点锁，但也不再提供自动工作区快照/回滚承诺。
- 没有累计自动续轮上限或暂停额度提示；仍按既有单轮步数限制执行并支持 Abort。容量不足是整批消息错误，队列变化后才重试，不截断、不拆批。
- 配置页、编辑器和运行面板应移除 v1/v2 等配置版本、归档恢复及显式采用更新的文案。运行面板若展示旧快照，不能仅凭“最新配置”文字认定已应用；以 Case 16 的实际请求和运行证据为准。
- transcript 损坏检查尚未统一覆盖只读历史及退出 Team 后的普通续聊；Case 22 对该项只验活跃 Team 提交时的检查，不把已知缺口列为已实现保护。
- 兼容性错误的 HTTP 状态码尚不完全统一，判定需结合真实 `code/message`；本文不预设所有冲突都返回 409。
