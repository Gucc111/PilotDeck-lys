## 1. 执行和判定规则

- 每个 case 的“首次覆盖的功能”只列之前未列过的功能；后续操作可能再次用到它们，但不重复计入覆盖。
- **真实使用**：真人操作真实 Web 页面，经过真实 Gateway、存储和实际配置的模型。既看流程，也看任务交付物是否合理。
- **辅助观察**：读取测试环境的请求记录、Team 记录和文件，或回放一次已捕获请求。界面没输出不能证明零模型调用；模型说“已完成”不能证明任务完成。
- **受控故障**：在独立测试环境中延迟请求、丢弃响应、断开浏览器、终止服务或替换模型输出。它验证异常分支，不能代替真实模型的协作效果验收。
- 每条功能分别记录：`通过 / 失败 / 部分覆盖 / 未触发 / 环境阻塞 / 未执行`。一个条目只完成部分分支时记“部分覆盖”；已出现的明确失败不能被其他成功分支抵消。允许更明确地重试，但保留失败或未触发的原始记录。

### 停止与重启的判定边界

**Abort 或 Gateway 重启后，旧运行中尚未应用的消息必须失效。无论接收者是 Leader 还是 Teammate，都不能由这些旧消息自动启动新回合，也不能在后续新回合中补投递。用户明确发送新请求后，当前运行产生的新消息可以正常激活接收者。**

- pending 指已登记但尚未实际应用的消息，包括 mailbox 已入队但尚未持久化应用的消息；以 `steer_applied`/对应 transcript 或内部输入的持久接纳为应用边界，不能仅凭 queued/owner 推断。中断前已经应用的消息可以保留在聊天历史中。
- 每个分支分两个观察窗口：先在没有新人工输入时检查旧消息不能自动唤醒；再明确发送新请求、产生当前代次的新消息，检查旧消息仍未补投递而新消息可以正常应用。Abort/Gateway 重启 × 接收者 Leader/Teammate 四种组合分别留证，未形成真实 pending 前态的分支不能算通过。
- 用 `activationId + stopVersion + message.id/teamEventIds` 关联旧消息、应用回执及接收回合；通知使用对应 notification/event ID。模型在新回合使用新 token 生成同文消息，会得到新的消息身份，应记录为新操作，不能按正文相同认定旧消息被重投。旧任务、通知、输入 token 和用户队列的其他保护仍按各 case 验证。
- 新回合中模型忽略当前请求、重发旧内容或重新调用旧命令，单列为“模型行为观察”，保留原 prompt、调用和真实效果；它不单独判定消息失效或停止/重启机制失败，也不保证新请求的任务交付成功。只有追踪到旧消息被自动启动/补投递、旧请求被重新接纳等程序行为，才判对应生命周期断言失败。
- transcript 的过滤、工具调用/结果配对补齐属于请求格式恢复行为；本组用例不预设必须采用某种恢复形式，也不凭恢复形式或模型表现直接认定上下文管理缺陷。

### 2.2 基准 Team

以下配置在 Case 01 中通过界面建立。其余 case 默认使用该配置的当前修订；需要改模型、权限或能力时，Fork 一个标有 case 编号的临时变体，避免污染其他用例。

| 对象 | 建议配置 |

### 2.3 如何留证

每个 case 保存一份简短记录：版本、环境、模型、配置修订、操作时间、会话 URL、输入原文、实际结果、逐条功能结论及证据位置。

- 用户可见证据：录屏/截图、Leader 最终回答、团队详情、实际生成文件、命令结果。
- 结构化证据：通过实际页面请求或 `team_command` 的 `library`、`runtime_get` 响应查看 ID、修订、任务和消息。Web 入口是 `POST /api/team-library`，沿用当前登录凭据；不要在报告中附带 Cookie、Token 或模型密钥。
- 人类交互保留完整 owner：`sessionKey + activationId + stopVersion + participantId + interactionId + requestId + kind`，以及请求快照、状态、响应和处理时间。Gateway 使用 `team_interaction_respond` / `team_participant_messages`；Web action 分别为 `runtime_interaction_respond` / `runtime_participant_messages`。记录 `runtime_get` 的返回及实际分页 cursor，不能只以 WebSocket 通知证明落盘。
- 区分专用 `team-interaction`、`team-interaction-updated`、`team-participant-message` 帧与 Leader 的普通权限帧。只读流记录 owner、消息/turn ID、`streamEpoch`、revision、订阅/退订和刷新前后内容；受控重放旧帧的结果不能冒充真实网络重连。
- `activation.id` 表示这一次进入 Team 模式的运行段，不是另一条聊天；`stopVersion` 表示该运行段的代次，输入、任务、消息、通知和停止请求均绑定原始代次；`work.id` 是任务，`message.id` 是消息，`requestToken/runId` 用于识别一次请求。测试者记录这些值，不手工发明产品身份。
- 请求回放保留捕获时的完整身份：`submit_turn`/steer/Abort 的 `teamActivationId + teamStopVersion`，以及 `runtime_stop` 的 `activationId + stopVersion`。测试驱动不能先读最新代次再替换旧请求，否则测不到过期请求拒绝；新人工请求才读取当前身份并使用新 token。
- 需要证明接纳次数时，检查主聊天 transcript 的 `accepted_input`；需要证明模型、工具实际运行次数时，另看相应调用记录。两者不是同一个计数。
- 运行中消息区分“写入消息记录”“邮箱入队”“实际应用”三个时点。保存稳定 `teamEventIds`、turn/item ID、`steer_applied` 及相应 transcript/下一次模型输入；只有匹配同一代次的应用确认才可判为中途交付。空闲时启动后续轮则看内部输入的持久接纳，两种路径不混算。
- Case 19、20 额外记录每条旧 pending 消息的接收角色、消息/事件 ID、原代次、入队/应用时间，以及停止/重启后的失效状态；关联后来每个接收回合的触发来源。记录无新输入窗口的起止时间与延迟放行点，再记录明确新输入及新消息身份；总调用数、正文相同或副作用计数变化均不能代替来源核对。
- 内部成员上下文在 `${PILOT_HOME}/team-runtime/contexts/`，运行记录在 `${PILOT_HOME}/team-runtime/state.json`，配置在 `${PILOT_HOME}/team-library/state.json`。只在测试副本中直接修改它们。

## 3. 用例

### Case 01：从零配置一支可复用的发布评审团队

**方式：** 真实使用＋辅助观察。先记录聊天文件数量、模型请求计数和 MCP 连接计数。

**操作与期望：**

1. 从侧栏“团队”进入 `Leaders`、`Teammates`，按基准先建立发布负责人和代码审查员，测试员留到步骤 4 创建。先试空显示名称或空系统提示词，再补齐保存；前者不能保存。
2. 两类角色都填写描述，切换默认/指定模型；模型支持时选择推理强度、速度。试选固定 P2，再改回继承。切换“能力清单来源”，确认它不改变工作区模式。用临时角色依次保存、读回三种“执行审批”选项，基准角色最终保持“需要时请求审批”。
3. 勾选工具、技能和 MCP 中各一个测试条目，标为“可选”，再取消其中一个能力；其可选标记也应消失。最终恢复基准能力。
4. 新建 Team，先试缺 Leader、没有 Teammate，确认不能保存。填写显示名称、描述、团队说明和默认工作区，选择一位 Leader；在 Team 编辑器内新建测试员，保存后回到原 Team 草稿且自动选中。
5. 保存并重新打开详情，核对字段、系统 ID 和修订；确认配置操作没有创建聊天或调用模型，保存能力选择也没有启动 MCP 业务工具。
6. 辅助回放非法保存请求：重复 Teammate、错误角色引用、不存在的修订、伪造新对象 ID、未知配置字段。记录字段错误，确认没有多出配置。

**首次覆盖的功能：**

- [ ] F001：可从零创建 Leader 和 Teammate，名称/系统提示必填，字段校验有效，ID 由服务端生成。
- [ ] F002：模型及可支持的参数、工作区继承/固定、能力允许列表和可选标记能够保存；能力清单来源仅影响展示。
- [ ] F003：Team 可组合一位 Leader 和至少一位不重复的 Teammate，保存说明和项目引用，并拒绝非法角色/修订/未知字段。
- [ ] F004：Team 编辑过程中可创建角色并返回原草稿，配置保存与聊天执行分离。

### Case 02：编辑到一半、保存失败和多人同时编辑

**方式：** 真实使用＋受控网络故障。使用临时配置，不改基准 Team。

**操作与期望：**

1. 分别填写一半角色草稿和 Team 草稿，不关闭编辑器，直接刷新浏览器；输入应恢复。随后点“放弃草稿”，刷新后不应再恢复。当前实现中编辑器 X/Esc 也会放弃该草稿。
2. 让能力清单请求失败，已有勾选仍保留，不能误以为空列表后覆盖配置；恢复请求并点重试。
3. 用代理或浏览器自动化让一次保存请求成功到达服务端，但丢弃响应。保存编辑器保留失败状态，字段冻结；点“重试”仍得到同一对象和修订，不新增副本。对一次 Fork 确认请求重复同样实验，保持名字不变再次点“复制并修改（Fork）”，副本只创建一次；Fork 确认窗口并不使用保存编辑器的“重试/新尝试”按钮。
4. 失败后需要改内容时，点击“作为新尝试继续编辑”。回放旧 token＋修改后参数应报冲突；新尝试可以保存。
5. 两个标签页同时编辑同一修订：A 先保存，B 再保存应报告修订冲突，不能覆盖 A；重新载入后再编辑。

**首次覆盖的功能：**

- [ ] F005：本机未关闭草稿可恢复，明确放弃后清除。
- [ ] F006：能力目录加载失败保留选择并可重试。
- [ ] F007：配置保存和 Fork 操作的重试 token 保持幂等，改参数须新尝试；响应丢失不重复创建。
- [ ] F008：旧修订并发保存被拒绝，不静默覆盖他人修改。

### Case 03：更新角色，并由 Team 明确采用

**方式：** 真实使用。记录更新前的角色和 Team 修订。

**操作与期望：**

1. 编辑发布负责人的显示名称、描述、提示词，以及模型支持时的一个参数，保存；ID 保持，修订增加。
2. 打开引用它的 Team，确认仍引用旧修订，显示“有更新”。进入“编辑”，点击角色行的“查看变化”，核对新旧字段。
3. 先关闭比较窗口，不保存；Team 仍不变。再点击“采用最新配置”并保存 Team，引用才更新。
4. 将 Team 的名称、说明、成员选择和默认工作区作一次合法编辑，确认 Team ID 保持、修订增加；随后恢复本轮基准配置。通过请求回放尝试把既有 Leader 改为 Teammate，应拒绝。

**首次覆盖的功能：**

- [ ] F009：角色和 Team 编辑生成新修订、保留身份；既有角色类型不能修改。
- [ ] F010：Team 固定角色修订，提供变化比较，只有显式采用并保存才更新引用。

### Case 04：复制角色与团队，为不同用途独立调整

**方式：** 真实使用＋配置读回。

**操作与期望：**

1. 分别 Fork 一位 Leader、一位 Teammate，命名“Case04…”。确认新 ID、初始修订和复制来源，修改副本提示词后原角色不变。
2. Fork 发布评审团队。新 Team 有独立 ID，但角色 ID/修订仍与源 Team 相同，角色数量不应凭空增加。
3. 在副本 Team 编辑器点击“复制所选角色”，调整该副本，保存 Team；原 Team 的角色引用不变。
4. 另做一次 Fork，确认后在自动打开的编辑器中“放弃草稿”：已创建副本仍存在，仅后续未保存编辑被放弃。项目文件和聊天历史均不被复制。

**首次覆盖的功能：**

- [ ] F011：Leader/Teammate Fork 创建独立身份并记录来源，修改互不影响。
- [ ] F012：Team Fork 创建独立 Team、复用角色修订；可在 Team 内单独 Fork 并替换角色，不复制文件或聊天。
- [ ] F013：Fork 确认即创建副本，取消后续编辑不撤销该副本。

### Case 05：归档和恢复配置，不破坏既有引用

**方式：** 真实使用＋配置读回＋请求回放；完成后恢复所需配置。

**操作与期望：**

1. 归档一个已被 Team 引用的角色。普通列表和新建 Team 的候选中不再出现；勾“显示已归档”可以找到，暂不恢复。
2. 归档期间，原 Team 仍能显示并保留原引用；新建界面不提供该角色候选，回放引用该角色的新建请求被拒绝，直接 Fork 原 Team 也失败。原 Team 在不换该引用的情况下保存其他字段应允许。随后恢复角色，确认可以再次用于新选择。
3. 归档一个 Team，刷新配置列表和聊天的 Team 菜单；它不再是新的选择。显示已归档后查看、恢复，角色引用及配置仍在。

**首次覆盖的功能：**

- [ ] F014：角色/Team 支持归档、筛选与恢复，归档不是删除配置。
- [ ] F015：归档对象不能用于新的选择，已有 Team 的固定角色引用保留；新 Team Fork 同样检查角色归档状态。

### Case 06：在新聊天的模型菜单选择 Team，暂不发送

**方式：** 真实使用＋调用计数。使用新空白聊天。

**操作与期望：**

1. 打开输入框右下角“选择模型或 Team”，搜索发布评审团队，确认团队分组显示名称、Leader 名称、成员数量。
2. 选中后查看兼容性和工作区，再取消：没有创建聊天或执行工作。重新选择并确认，按钮显示 Team 名称；保持输入未发送，模型调用计数不变。

1. Leader 已结束但成员仍在工作时，输入框无草稿应仍可点击停止；有草稿时可在未打开模态窗口的情况下用 Esc。停止覆盖整队：运行/排队/等待任务终止，旧普通消息、催办、回复、自动通知和续作失效；Team 用户排队输入显示“已失效”，不能点击继续队列、重试原 token 或 steer。普通会话的队列语义不变。
2. 停止前分别确认两种接收角色的消息已经登记、尚未应用，保存原代次与消息/事件 ID；另覆盖 mailbox 已入队但尚未应用、未投递完成通知。停止后先不发送新请求，放行先前延迟的消息投递、工具响应和网络响应，确认旧消息失效且没有对应的新 `steer_applied`/内部接纳，不能激活 Leader 或 Teammate，也不能恢复旧任务或触发自动续答。已经产生的文件副作用不要求自动撤销，记录其发生时间。仅有任务/用户队列而没有内部 pending 消息，不算覆盖这两个消息方向。
3. 在预检或会话准备阶段设置明确阻塞点：发起输入→点击停止→再放行准备步骤；旧输入不能被接纳或调用模型，停止状态不能被旧回调覆盖。
4. 人为让一个工具迟迟不响应取消，另以授权测试 MCP 延迟资源关闭。界面及 runtime 必须保持“正在停止”；默认等待超过 30 秒仍未退出时显示清理超时及待清理对象，不能以任务已标为 stopped 代替实际退出。清理失败应保留错误并可重试；在执行、消息投递或 MCP 清理仍未结束时，发送新请求及切换模式均须拒绝。重试同一个停止请求不应再次增加 stopVersion。
5. 清理完成后发送明确的新用户请求，可继续 Team；此前停止的任务保持原状态。对失效用户输入点“放回输入框”，检查文本与附件引用保留，明确发送使用新 token。保存新请求已接纳及启动模型的证据后，再回放旧 Abort，不能停止新运行；旧清理回调也不能删除新执行登记。为两种接收角色分别产生当前代次的新消息，确认它们可以正常应用/激活，同时步骤 2 的旧消息仍未补投递。按消息身份关联来源；新回合重新生成同文消息或旧命令时单列模型行为，不据此推断旧消息被重投。
6. 在首次 Team 输入尚未建立 activation 的准备阶段停止，排队的同选择后续输入也必须失效，不能等预检放行后启动旧请求。

本次交互子分支：在权限、问题、Plan 请求已真实落盘且 pending 时停止，保存停止前后的同一 interaction 及 stopVersion。界面显示 cancelled 历史，旧卡片和旧响应均不能恢复原执行；Leader 的普通审批与成员交互不可混淆。此项计入 Case 14 F045，不能据此宣称本例全部消息/清理竞态已覆盖，不执行 F060 的旧操作重放验收。

**首次覆盖的功能：**

- [ ] F059：停止覆盖整队、待处理内部消息/通知和 Team 用户队列；旧 pending 消息既不能激活 Leader/Teammate，也不能在新回合中补投递，当前代次新消息可以正常应用；失效用户输入只可显式放回输入框后用新 token 发送，文本及附件引用保留。
- F060（非缺陷，本期排除）：保留编号追溯历史结论，不纳入 Team 人类交互面板修复与验收。

### Case 20：浏览器断线、服务重启和中断任务恢复

> F063 经进一步调研和用户确认不属于缺陷，本期排除。Case 20 其余步骤仅保留作既有生命周期回归参考；本次新增交互过期与只读恢复由 Case 14 / 14A 验证。

**方式：** 真实使用＋隔离服务重启。分支之间用独立聊天，避免相互干扰。

**操作与期望：**

1. 长任务已启动后关闭浏览器或断开 WebSocket，保持服务运行。等任务及 Leader 最终回答结束后，直接打开原 URL，身份、任务、结果和最终回答可读；无成员公开聊天。刷新不应触发新的模型调用。
2. 确认任务全部终结、消息处理完、通知已确认、Leader 最终回答结束且无待发输入，再正常重启服务，直接打开原 URL 读取主聊天和面板。既测侧栏首屏内的聊天，也测未加载分页中的旧聊天；不点击“加载更多”辅助恢复。对照重启前记录：聊天内容不变，没有因“查看”而新增模型调用；运行段可保持同一 ID，但重启后停止状态及递增代次不要求与重启前完全一致。仅任务 completed 并不足以满足静止条件。
3. 在成员已向只追加日志记录一次副作用、尚未结算结果时强制结束测试服务。重启后该任务为 `interrupted`，不自动重做该副作用；不生成会唤醒 Leader 的恢复通知。保存唯一调用 ID、进程、时间及计数，不能只依据状态截图或可被覆盖的单一文件。服务进程终止不等于外部子进程自动消失，记录并最终清理本次测试创建的 gate。
4. 同时安排尚未领取的 queued 工作；按 Case 19 的消息取证方法，分别构造发给 Leader、发给 Teammate 的普通 pending 消息、关联回复及未投递通知，覆盖 mailbox 入队但未应用的边界。保存原消息/事件 ID、代次及尚未应用的前态。Gateway 重启后 queued 工作也必须中断，所有旧 pending 消息/通知失效；在无新输入窗口释放延迟投递，不能由它们激活任一接收角色，也不能产生恢复唤醒。已经完成的结果与已应用历史仍可查看。
5. 在等待人工审批时重启服务，原执行中断，旧审批或补充信息回复不能续作；不恢复旧审批 Promise。用户需要时明确发起新工作。
6. 分别只重启 Gateway、只重启 Web bridge：Team 用户队列（包括仅有 teamSelection、尚未建立 activation 的输入）均失效；文本和附件引用保留。记录各服务 PID/instanceId，确认确实重启了目标进程。仅重启 Web bridge 的分支重点检查其用户队列，不将仍存活 Gateway 中的运行任务一概按重启中断处理；Gateway 恢复才检查步骤 3–5 的运行记录失效。普通聊天队列仍按原暂停恢复规则处理。只断开并重连浏览器或 bridge 到同一个 Gateway 的连接，不算进程重启，不应据此使有效 Team 输入失效。
7. 先保持无新人工输入，确认旧任务、消息和通知不会自动启动；再明确发送新请求，核对新代次实际可用，并分别向 Leader/Teammate 发送当前代次的新消息。新消息可正常激活接收者，步骤 4 的旧消息仍不能补投递，旧 queued 工作不会被程序重新调度。旧请求、旧回答和旧 token 的回放不能改变新执行。若新回合模型重发旧内容或重做旧命令，保存新 token、消息/调用 ID、turn 和副作用记录，单列模型行为；不以新输入之后总副作用计数不变作为消息失效断言。重启前已执行的外部进程是否仍存活另行记录，不与新调用混为一谈。

本次定向复验只更新实际执行的子分支：浏览器刷新/真实断线不使仍有效的 pending 交互过期；Gateway 重启后 pending 变为 expired，已处理记录和请求快照保留。仅 Web bridge 重启且 Gateway 未重启时，不能据此推断等待句柄失效。分别直接打开侧栏首屏外的 root URL 和成员只读 URL，记录 Team 身份、transcript 与只读限制；此项同时复验 10/26 的分页外 URL 缺陷。交互状态归 Case 14 F045，只读恢复归 Case 14A F078；没有实际重启的分支标明未执行，不执行 F063 的旧操作重放验收。

**首次覆盖的功能：**

- [ ] F061：浏览器断线只影响观察，服务器仍执行；重开/刷新可恢复身份、任务、通信和结果。
- [ ] F062：已完成 Team 在服务重启后可读恢复，查看结果不产生新模型执行。
- F063（非缺陷，本期排除）：保留编号追溯历史结论，不纳入 Team 人类交互面板修复与验收。

### Case 21：自动续答有上限，通知失败不会丢失或重复执行

**方式：** 受控端到端。需要可控的成员完成节奏与通知接纳响应；不依赖真实模型自由聊天恰好产生足够轮次。

**操作与期望：**

1. 持续制造成员结果/消息。分别记录当前回合内应用的消息与真正启动的新 Leader 后续轮；前者不消耗自动唤醒额度。为触发上限，每次等 Leader 空闲并由通知启动后续轮，再释放下一批。

## 4. 当前边界与已知问题

执行时用本节解释范围，不能将以下未支持功能计为漏测或通过：

- 当前没有可输入的独立成员聊天、成员直连开关、动态招募/删除运行成员、同角色多实例、Leader 自动审批、分层权限治理、在线蓝图编辑或甘特图。Teammate 只读聊天仅用于展示 transcript 和流式输出。
- Leader 与运行中的 Teammate 使用内部邮箱，在安全边界处理消息；不能改写已发出的模型请求或拆开工具调用与结果。未强制 Leader 保持存活，也未增加 sleep/等待工具或改造 team_collect 轮询。面板刷新只读取状态。
- 能力设置约束工具接口、技能入口和 MCP 接入，不能代替操作系统沙箱。共享项目文件不天然隔离；禁止工具桥接口也不保证其他获授权执行接口无法操作同一文件。
- 服务仍运行时的浏览器刷新可恢复审批；Abort/服务重启使旧消息、通知、审批回复及未完成任务失效。共享目录没有整轮检查点锁，但也不再提供自动工作区快照/回滚承诺。
- 当前没有供用户设置自动续答预算的界面。Case 21 的默认上限为 24 次真正启动的 Leader 后续轮；开发测试若注入更小上限，只能算状态机辅助证据，不能声称验证了默认 24 次端到端行为。
- 截至此版本，配置页仍有“团队运行、任务委派和成员通信尚未实现”的过期说明；空默认工作区选项也仍写“所有成员必须固定项目”。实际上可以从模型菜单进入 Team，通用聊天可以在预检中选择执行项目。这两处是已发现的文案问题，验收应记录，不应据此判定运行功能不存在。
- transcript 损坏检查尚未统一覆盖只读历史及退出 Team 后的普通续聊；Case 22 对该项只验活跃 Team 提交时的检查，不把已知缺口列为已实现保护。
- 兼容性错误的 HTTP 状态码尚不完全统一，判定需结合真实 `code/message`；本文不预设所有冲突都返回 409。
