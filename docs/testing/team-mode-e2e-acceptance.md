# Team 模式：实际使用与端到端验收用例

编写日期：2026-10-23；行为核对：2026-10-26。本轮验收以撤销工作区检查点、Team 中途消息注入及运行代次失效机制的当前工作区代码为基线；实际执行时记录提交、未提交改动及运行构建，不能仅凭相同 Git 提交判定服务已加载新行为。旧报告对应旧版本，不作为本轮通过证据。

本文用于组织一次新的验收，不是已通过的测试报告。所有条目初始状态均为“未执行”。以当前实现和 [Team 使用说明](../team-mode.md) 为范围，`docs/research/` 中的 DSH 调研只作背景，不把其尚未移植的能力列为已实现功能。

最新执行结果：[2026-10-26 实测报告](reports/2026-10-26-team-cases01-20/README.md)与[逐功能证据](reports/2026-10-26-team-cases01-20/feature-results.md)。历史结果：[2026-10-23 Case 01–20](reports/2026-10-23-team-cases01-20/README.md)；[2026-10-24 Case 09–20 补跑报告](reports/2026-10-24-team-cases09-20/README.md)与[逐功能证据](reports/2026-10-24-team-cases09-20/feature-results.md)。下面的复用检查项不代替报告结论；补跑包含实际失败及未覆盖分支，旧结果不自动计入新一轮通过数。

贯穿例子是“发布评审团队”：用户在原聊天提出发布检查请求，Leader 组织审查员、测试员工作，处理成员之间的问题，最后交付一份能据此做发布决定的报告。

## 1. 执行和判定规则

- 按 Case 01 → 25 执行。每个 case 的“首次覆盖的功能”只列之前未列过的功能；后续操作可能再次用到它们，但不重复计入覆盖。
- **真实使用**：真人操作真实 Web 页面，经过真实 Gateway、存储和实际配置的模型。既看流程，也看任务交付物是否正确。
- **辅助观察**：读取测试环境的请求记录、Team 记录和文件，或回放一次已捕获请求。界面没输出不能证明零模型调用；模型说“已完成”不能证明任务完成。
- **受控故障**：在独立测试环境中延迟请求、丢弃响应、断开浏览器、终止服务或替换模型输出。它验证异常分支，不能代替真实模型的协作效果验收。
- 每条功能分别记录：`通过 / 失败 / 部分覆盖 / 未触发 / 环境阻塞 / 未执行`。模型没有实际委派、没有发出指定工具调用、任务太快未产生并行等，一律记“未触发”，不能记通过。一个条目只完成部分分支时记“部分覆盖”；已出现的明确失败不能被其他成功分支抵消。允许更明确地重试，但保留失败或未触发的原始记录。
- `completed` 只说明一次成员执行正常结束并保存了结果；还必须核对文件、测试结果、引用证据。消息“已送达”也不等于获得答复或完成任务。
- 普通路径不要求修改请求。涉及身份、权限、重试边界时，按对应 case 使用请求回放；只验证前端按钮禁用不等于验证服务端约束。

### 2.2 基准 Team

以下配置在 Case 01 中通过界面建立。其余 case 默认使用该配置的当前修订；需要改模型、权限或能力时，Fork 一个标有 case 编号的临时变体，避免污染其他用例。

| 对象 | 建议配置 |
| --- | --- |
| Leader“发布负责人” | M-L；继承 Team 工作区；`read_file`、`write_file`；执行审批为“需要时请求审批” |
| Teammate“代码审查员” | M-R；继承工作区；`read_file`、`glob`、`grep`；需要时请求审批 |
| Teammate“测试员” | M-T；继承工作区；`read_file`、`bash`；需要时请求审批 |
| Team“发布评审团队” | 一位上述 Leader、两位上述 Teammate，默认 P1；团队说明要求区分事实与推断，读取成员结果后汇总 |

角色提示词分别明确职责和输出要求。例如 Leader 写“先分配独立的审查和测试任务，收集实际结果后生成报告”；审查员写“引用文件和问题位置”；测试员写“报告真实命令、退出结果和失败样例，不把失败测试改成通过”。后续 case 可临时增加更具体的协作要求。

### 2.3 如何留证

每个 case 保存一份简短记录：版本、环境、模型、配置修订、操作时间、会话 URL、输入原文、实际结果、逐条功能结论及证据位置。

- 用户可见证据：录屏/截图、Leader 最终回答、团队详情、实际生成文件、命令结果。
- 结构化证据：通过实际页面请求或 `team_command` 的 `library`、`runtime_get` 响应查看 ID、修订、任务和消息。Web 入口是 `POST /api/team-library`，沿用当前登录凭据；不要在报告中附带 Cookie、Token 或模型密钥。
- `activation.id` 表示这一次进入 Team 模式的运行段，不是另一条聊天；`stopVersion` 表示该运行段的代次，输入、任务、消息、通知和停止请求均绑定原始代次；`work.id` 是任务，`message.id` 是消息，`requestToken/runId` 用于识别一次请求。测试者记录这些值，不手工发明产品身份。
- 请求回放保留捕获时的完整身份：`submit_turn`/steer/Abort 的 `teamActivationId + teamStopVersion`，以及 `runtime_stop` 的 `activationId + stopVersion`。测试驱动不能先读最新代次再替换旧请求，否则测不到过期请求拒绝；新人工请求才读取当前身份并使用新 token。
- 需要证明接纳次数时，检查主聊天 transcript 的 `accepted_input`；需要证明模型、工具实际运行次数时，另看相应调用记录。两者不是同一个计数。
- 运行中消息区分“写入消息记录”“邮箱入队”“实际应用”三个时点。保存稳定 `teamEventIds`、turn/item ID、`steer_applied` 及相应 transcript/下一次模型输入；只有匹配同一代次的应用确认才可判为中途交付。空闲时启动后续轮则看内部输入的持久接纳，两种路径不混算。
- 内部成员上下文在 `${PILOT_HOME}/team-runtime/contexts/`，运行记录在 `${PILOT_HOME}/team-runtime/state.json`，配置在 `${PILOT_HOME}/team-library/state.json`。只在测试副本中直接修改它们。

## 3. 用例

### Case 01：从零配置一支可复用的发布评审团队

**方式：** 真实使用＋辅助观察。先记录聊天文件数量、模型请求计数和 MCP 连接计数。

**操作与期望：**

1. 从侧栏“团队”进入 `Leaders`、`Teammates`，按基准先建立发布负责人和代码审查员，测试员留到步骤 4 创建。先试空显示名称或空系统提示词，再补齐保存；前者不能保存。
2. 两类角色都填写描述，切换默认/指定模型；模型支持时选择推理强度、速度。试选固定 P2，再改回继承。切换“能力清单来源”，确认它不改变工作区模式。用临时角色依次保存、读回三种“执行审批”选项，基准角色最终保持“需要时请求审批”。
3. 勾选工具、技能和 MCP 中各一个测试条目，标为“可选”，再取消其中一个能力；其可选标记也应消失。最终恢复基准能力。
4. 新建 Team，先试缺 Leader、没有 Teammate，确认不能保存。填写显示名称、描述、团队说明和默认工作区，选择一位 Leader；在 Team 编辑器内新建测试员，保存后回到原 Team 草稿且自动选中。
5. 保存并重新打开详情，核对字段、系统 ID 和修订；确认配置操作没有创建聊天或调用模型，保存能力选择也没有启动 MCP 业务工具。
6. 辅助回放非法保存请求：重复 Teammate、错误角色引用、不存在的修订、伪造新对象 ID、未知配置字段。记录字段错误，确认没有多出配置。

**首次覆盖的功能：**

- [ ] F001：可从零创建 Leader 和 Teammate，名称/系统提示必填，字段校验有效，ID 由服务端生成。
- [ ] F002：模型及可支持的参数、工作区继承/固定、能力允许列表和可选标记能够保存；能力清单来源仅影响展示。
- [ ] F003：Team 可组合一位 Leader 和至少一位不重复的 Teammate，保存说明和项目引用，并拒绝非法角色/修订/未知字段。
- [ ] F004：Team 编辑过程中可创建角色并返回原草稿，配置保存与聊天执行分离。

### Case 02：编辑到一半、保存失败和多人同时编辑

**方式：** 真实使用＋受控网络故障。使用临时配置，不改基准 Team。

**操作与期望：**

1. 分别填写一半角色草稿和 Team 草稿，不关闭编辑器，直接刷新浏览器；输入应恢复。随后点“放弃草稿”，刷新后不应再恢复。当前实现中编辑器 X/Esc 也会放弃该草稿。
2. 让能力清单请求失败，已有勾选仍保留，不能误以为空列表后覆盖配置；恢复请求并点重试。
3. 用代理或浏览器自动化让一次保存请求成功到达服务端，但丢弃响应。保存编辑器保留失败状态，字段冻结；点“重试”仍得到同一对象和修订，不新增副本。对一次 Fork 确认请求重复同样实验，保持名字不变再次点“复制并修改（Fork）”，副本只创建一次；Fork 确认窗口并不使用保存编辑器的“重试/新尝试”按钮。
4. 失败后需要改内容时，点击“作为新尝试继续编辑”。回放旧 token＋修改后参数应报冲突；新尝试可以保存。
5. 两个标签页同时编辑同一修订：A 先保存，B 再保存应报告修订冲突，不能覆盖 A；重新载入后再编辑。

**首次覆盖的功能：**

- [ ] F005：本机未关闭草稿可恢复，明确放弃后清除。
- [ ] F006：能力目录加载失败保留选择并可重试。
- [ ] F007：配置保存和 Fork 操作的重试 token 保持幂等，改参数须新尝试；响应丢失不重复创建。
- [ ] F008：旧修订并发保存被拒绝，不静默覆盖他人修改。

### Case 03：更新角色，并由 Team 明确采用

**方式：** 真实使用。记录更新前的角色和 Team 修订。

**操作与期望：**

1. 编辑发布负责人的显示名称、描述、提示词，以及模型支持时的一个参数，保存；ID 保持，修订增加。
2. 打开引用它的 Team，确认仍引用旧修订，显示“有更新”。进入“编辑”，点击角色行的“查看变化”，核对新旧字段。
3. 先关闭比较窗口，不保存；Team 仍不变。再点击“采用最新配置”并保存 Team，引用才更新。
4. 将 Team 的名称、说明、成员选择和默认工作区作一次合法编辑，确认 Team ID 保持、修订增加；随后恢复本轮基准配置。通过请求回放尝试把既有 Leader 改为 Teammate，应拒绝。

**首次覆盖的功能：**

- [ ] F009：角色和 Team 编辑生成新修订、保留身份；既有角色类型不能修改。
- [ ] F010：Team 固定角色修订，提供变化比较，只有显式采用并保存才更新引用。

### Case 04：复制角色与团队，为不同用途独立调整

**方式：** 真实使用＋配置读回。

**操作与期望：**

1. 分别 Fork 一位 Leader、一位 Teammate，命名“Case04…”。确认新 ID、初始修订和复制来源，修改副本提示词后原角色不变。
2. Fork 发布评审团队。新 Team 有独立 ID，但角色 ID/修订仍与源 Team 相同，角色数量不应凭空增加。
3. 在副本 Team 编辑器点击“复制所选角色”，调整该副本，保存 Team；原 Team 的角色引用不变。
4. 另做一次 Fork，确认后在自动打开的编辑器中“放弃草稿”：已创建副本仍存在，仅后续未保存编辑被放弃。项目文件和聊天历史均不被复制。

**首次覆盖的功能：**

- [ ] F011：Leader/Teammate Fork 创建独立身份并记录来源，修改互不影响。
- [ ] F012：Team Fork 创建独立 Team、复用角色修订；可在 Team 内单独 Fork 并替换角色，不复制文件或聊天。
- [ ] F013：Fork 确认即创建副本，取消后续编辑不撤销该副本。

### Case 05：归档和恢复配置，不破坏既有引用

**方式：** 真实使用＋配置读回＋请求回放；完成后恢复所需配置。

**操作与期望：**

1. 归档一个已被 Team 引用的角色。普通列表和新建 Team 的候选中不再出现；勾“显示已归档”可以找到，暂不恢复。
2. 归档期间，原 Team 仍能显示并保留原引用；新建界面不提供该角色候选，回放引用该角色的新建请求被拒绝，直接 Fork 原 Team 也失败。原 Team 在不换该引用的情况下保存其他字段应允许。随后恢复角色，确认可以再次用于新选择。
3. 归档一个 Team，刷新配置列表和聊天的 Team 菜单；它不再是新的选择。显示已归档后查看、恢复，角色引用及配置仍在。

**首次覆盖的功能：**

- [ ] F014：角色/Team 支持归档、筛选与恢复，归档不是删除配置。
- [ ] F015：归档对象不能用于新的选择，已有 Team 的固定角色引用保留；新 Team Fork 同样检查角色归档状态。

### Case 06：在新聊天的模型菜单选择 Team，暂不发送

**方式：** 真实使用＋调用计数。使用新空白聊天。

**操作与期望：**

1. 打开输入框右下角“选择模型或 Team”，搜索发布评审团队，确认团队分组显示名称、Leader 名称、成员数量。
2. 选中后查看兼容性和工作区，再取消：没有创建聊天或执行工作。重新选择并确认，按钮显示 Team 名称；保持输入未发送，模型调用计数不变。
3. 刷新空白页，Team 选择和本机保留的首次发送身份仍在；侧栏没有成员聊天，尚未产生执行任务。
4. 在 `empty-home` 环境选择已有的“无项目团队”，应引导登记项目，不能用通用目录代替执行项目。
5. 受控延迟 Team A 的预检，取消后选 Team B，再返回 A 的旧响应；界面不能被 A 覆盖。模拟模型目录请求失败但 Team 目录成功，菜单仍可查看 Team。

**首次覆盖的功能：**

- [ ] F016：模型菜单提供 Team 分组、名称展示和统一搜索，Team 目录不依赖普通模型目录成功。
- [ ] F017：空白聊天先选择后发送；取消无执行副作用，未发送选择在本机刷新后恢复。
- [ ] F018：无已登记项目时有明确引导，旧预检响应不能覆盖新选择。

### Case 07：已有项目聊天与通用聊天在原处进入 Team

**方式：** 真实使用＋目录/请求观察。

**操作与期望：**

1. 在 P1 普通聊天先发送“这次发布编号为 R-17”，输入下一条草稿但不发送。选择 Team 后确认 URL、历史、草稿不变。请 Leader 复述编号，检查它沿用当前聊天上下文。
2. P1 聊天的项目选择固定；试选 Leader 固定 P2 的临时 Team，应因工作区冲突阻断。
3. 在已有通用聊天选择 Team，明确选择 P1。让 Leader 读取相对路径 `workspace-tag.txt`，应读到 `APP_WORKSPACE`；会话仍归通用聊天存储，不搬移历史。
4. 使用一个 Teammate 固定 P2 的变体，请其读取同名相对路径，应得到 `DOCS_WORKSPACE`；其余继承角色仍使用 P1。
5. 针对 **P1 项目聊天**回放请求：把预检/选择的 `storageProjectKey`、选择的执行 `projectKey`、发送外层的存储 `projectKey` 或 `workspaceCwd` 改成 P2/P0，真实归属不能被替换。省略位置时服务端仍定位原聊天，不在伪造位置产生第二份历史。通用聊天在选择阶段合法改选已登记 P2 并重新预检确认是允许路径，不应误判为篡改。

**首次覆盖的功能：**

### Case 13：成员之间并行，同一成员内部串行

**方式：** 真实使用＋可控延迟工具。提示模型“同时做”不足以证明并行。

**操作与期望：**

1. 临时为审查员、测试员授权 `bash`，在 P1 运行现成的 `python3 qa_gate.py <任务标签>`，每轮使用新标签。脚本在 `out/gates/` 写入 `<任务标签>.started` 后等待放行，结束后写入 `.finished`；测试者在 P1 执行 `touch out/gates/<任务标签>.release` 放行。工具超时须覆盖计划等待时长（脚本最多等待 180 秒）；若命令转入后台，仅有 `.started` 不能证明成员执行仍被占用。
2. 让 Leader 按顺序等待每项委派接纳，再委派审查员 A1、测试员 B1、审查员 A2；这里不等待任务完成。等 A1/B1 都进入延迟工具，读取任务状态和 `.started` 时间：A1/B1 执行重叠，A2 尚未启动。必须按实际接纳顺序确认同成员串行，不能把并发工具调用的数组顺序或任务名称当作接纳顺序。
3. 先释放 B1，让其完成，此时 A1 仍等待；确认 B1 的结果可以落盘。再释放 A1，A2 才能进入执行。
4. 分别在 Leader 空闲、LLM 请求进行中、工具执行中及结束前边界释放成员结果。忙碌时消息先进入内部邮箱，在下一处安全边界写入上下文，保留工具调用与结果配对；已经发出的 LLM 请求不被改写。保存匹配该通知的 `steer_applied` 和下一次模型输入，确认 runtime 未在仅入队时提前写 delivered。若本轮结束前尚未应用且代次仍有效，应保留后续轮投递路径，最终只应用一次。
5. 同样在 Teammate 执行中送达一条带随机标记的明确协调消息，确认该成员当前 turn 在安全边界产生 `steer_applied`，后续实际输出能使用该标记；不能把另开一个成员 turn 代替中途应用。再覆盖成员尚在准备、消息首次尝试早于可投递状态的分支，模型执行就绪后消息仍应重试应用。内部消息带发送者及关联，不显示为人类聊天气泡，不结算用户排队输入。

7. 在独立分支让 A1 的模型调用遇到明确不可恢复错误，B1 保持正常。A1 应为 `failed` 并保存错误，B1 可以完成，A2 在 A1 退出后仍可执行；Leader 得知失败并说明哪些结果缺失，不能将全队汇总为成功。普通测试命令退出非零不必然使成员任务 failed，故本分支使用真实执行层失败。

**首次覆盖的功能：**

5. 另移除已冻结的一项可选能力，后续执行应要求重新检查选择。面板“刷新”只读取状态，不等于重新预检；停止旧工作后重新选择 Team、确认限制，建立新运行段再继续。

**首次覆盖的功能：**

- [ ] F050：浏览器与 Team 的模型选择相互隔离，不污染普通聊天默认值；默认角色模型在进入时解析并冻结。
- [ ] F051：运行快照与后续配置编辑/归档分离，旧聊天继续使用既定角色、说明和版本。
- [ ] F052：续聊、成员启动和配置重载重新核验运行条件，变化不会静默降级，需重新选择确认后生效。

### Case 17：忙碌时保持模式，空闲后切换并查看旧记录

**方式：** 真实使用＋旧请求回放。

**操作与期望：**

1. 分别在 Leader 执行、成员排队/运行/等待信息/等待审批、消息待消费时尝试换 Team 或普通模型，应阻止。再在 Web 输入队列有待发消息时直接请求切换，后端也应拒绝。
2. 所有工作和消息处理完毕后，选普通模型，当前聊天可以普通续聊；团队历史入口仍可查看旧任务和消息。
3. 再选择另一 Team，或重新进入原 Team。当前聊天 URL 保持，但生成新运行段；历史选择器可区分各段。
4. 分别回放旧 activation、同一 activation 内旧 stopVersion、缺失必要代次字段的未接纳输入及 steer；另在当前 Team 活跃时提交显式 `null` 的旧普通模式输入。均应明确拒绝且不触发模型，不能发给新 Team。已持久接纳输入的只读重试另按 Case 18 判断。点击发送后，在命令展开或请求处理阶段设置受控延迟再尝试切换，最终执行选择须与该次发送的快照一致。附件尚未上传完成时当前 UI 会阻止发送，不能把这一阶段当成已发送输入测验。

**首次覆盖的功能：**

- [ ] F053：未完成工作、待处理消息及待发输入期间不能切换执行模式，前后端均检查。
- [ ] F054：空闲时可退出/换 Team，同一聊天保留可查看的历史运行段，再进入生成新身份。
- [ ] F055：发送与排队输入绑定当时的 Team 身份和代次，旧运行段/代次及旧普通模式输入不能误投到新模式。

### Case 18：首次发送、响应丢失和重复提交

**方式：** 真实页面＋请求回放/断网。先选好 Team，发送只读取测试数据的任务，记录首次 root、选择 token 和输入 runId。

**操作与期望：**

1. 首次发送在接纳前失败，页面显示错误并保留可重试输入；重试使用既定会话身份，不生成第二条聊天。成功后正确清除待重试状态。
2. 并发重放完全相同的选择和发送请求，再模拟服务端已接纳但客户端收不到接纳响应。并发期间允许返回“会话忙碌”；原请求结束或连接恢复后再用原 token 重试，最终仍是同一个运行段和一条 `accepted_input`，模型不重复执行该输入。
3. 服务重启后再逐字回放已经持久化接纳的原输入（包括原代次），只返回历史接纳信息，不重新激活 Team。另用尚未接纳的旧代次输入和选择收据回放，应拒绝；不能为其自动替换当前代次。选择重试使用 `requestToken`，输入重试使用 `runId`；分别修改 Team 选择或输入文字/附件但保留对应 token，应报冲突，错误码可因所在层不同而不同。对照 transcript 与模型/工具计数，不能把重试响应再次出现 `input_accepted` 当成第二次真实接纳。新任务使用新 token。
4. 对 Web 排队输入重复同 token 的同内容和改内容请求，队列/已接纳记录也须给出一致结果，不重复加入。
5. 另在输入已落盘、执行未可靠结束时中断服务，再用原 token 重试。应告知“已接纳但执行中断”并引导在原聊天明确继续，不能自动重放旧任务。
6. 在受控模型分支分别让委派、后续任务、发消息和转交工具重试：同一角色、同一运行段、同一显式 `requestToken` 及同内容应返回已有任务/消息，不新增记录；改变内容保留 token 应冲突。同一有效代次内重试仍不重复接纳；保存记录并重启后，旧角色和操作 token 已失效，不能续作或重新接纳。这是内部 Team 工具调用，不是向 `team_command` 发送不存在的委派 action。

**首次覆盖的功能：**

- [ ] F056：首次发送可恢复，接纳前失败保留输入且保持主聊天身份，成功接纳后清理重试状态。
- [ ] F057：创建选择、主输入、Web 输入队列及内部委派/消息操作持久化去重，同 token 改内容被拒绝，涵盖并发、响应丢失和重启重试。
- [ ] F058：已接纳但执行中断可被识别，不自动重新提交；接纳一次不被误解释为所有外部副作用恰好一次。

### Case 19：停止整个 Team，旧请求不能把它唤醒

**方式：** 真实使用＋受控延迟。建立运行、排队和等待答复的混合任务，另留一条待发用户输入。

**操作与期望：**

1. Leader 已结束但成员仍在工作时，输入框无草稿应仍可点击停止；有草稿时可在未打开模态窗口的情况下用 Esc。停止覆盖整队：运行/排队/等待任务终止，旧普通消息、催办、回复、自动通知和续作失效；Team 用户排队输入显示“已失效”，不能点击继续队列、重试原 token 或 steer。普通会话的队列语义不变。
2. 放行先前延迟的工具响应和网络响应。它们不能恢复旧任务，也不能触发 Leader 自动续答。已经产生的文件副作用不要求自动撤销，记录其发生时间。
3. 在预检或会话准备阶段设置明确阻塞点：发起输入→点击停止→再放行准备步骤；旧输入不能被接纳或调用模型，停止状态不能被旧回调覆盖。
4. 人为让一个工具迟迟不响应取消，另以授权测试 MCP 延迟资源关闭。界面及 runtime 必须保持“正在停止”；默认等待超过 30 秒仍未退出时显示清理超时及待清理对象，不能以任务已标为 stopped 代替实际退出。清理失败应保留错误并可重试；在执行、消息投递或 MCP 清理仍未结束时，发送新请求及切换模式均须拒绝。重试同一个停止请求不应再次增加 stopVersion。
5. 清理完成后发送明确的新用户请求，可继续 Team；此前停止的任务保持原状态。对失效用户输入点“放回输入框”，检查文本与附件引用保留，明确发送使用新 token。保存新请求已执行的证据后，再回放旧 Abort，不能停止新运行；旧清理回调也不能删除新执行登记。新的明确工作可引用旧结果，但旧任务和旧消息不会因此重新入队。
6. 在首次 Team 输入尚未建立 activation 的准备阶段停止，排队的同选择后续输入也必须失效，不能等预检放行后启动旧请求。

**首次覆盖的功能：**

- [ ] F059：停止覆盖整队及所有待处理内部消息/通知和 Team 用户队列；失效输入只可显式放回输入框后用新 token 发送，文本及附件引用保留。
- [ ] F060：停止以实际执行及清理完成为边界，超时保持清理中；迟到结果、旧 Abort、旧回调和准备阶段竞态不能影响新代次，新人工输入不重放旧任务。

### Case 20：浏览器断线、服务重启和中断任务恢复

**方式：** 真实使用＋隔离服务重启。分支之间用独立聊天，避免相互干扰。

**操作与期望：**

1. 长任务已启动后关闭浏览器或断开 WebSocket，保持服务运行。等任务及 Leader 最终回答结束后，直接打开原 URL，身份、任务、结果和最终回答可读；无成员公开聊天。刷新不应触发新的模型调用。
2. 确认任务全部终结、消息处理完、通知已确认、Leader 最终回答结束且无待发输入，再正常重启服务，直接打开原 URL 读取主聊天和面板。既测侧栏首屏内的聊天，也测未加载分页中的旧聊天；不点击“加载更多”辅助恢复。对照重启前记录：聊天内容不变，没有因“查看”而新增模型调用；运行段可保持同一 ID，但重启后停止状态及递增代次不要求与重启前完全一致。仅任务 completed 并不足以满足静止条件。
3. 在成员已向只追加日志记录一次副作用、尚未结算结果时强制结束测试服务。重启后该任务为 `interrupted`，不自动重做该副作用；不生成会唤醒 Leader 的恢复通知。保存唯一调用 ID、进程、时间及计数，不能只依据状态截图或可被覆盖的单一文件。服务进程终止不等于外部子进程自动消失，记录并最终清理本次测试创建的 gate。
4. 同时安排尚未领取的 queued 工作、普通催办消息、关联回复及未投递通知。重启后 queued 工作也必须中断，所有旧消息/通知失效；不能因催办另起一次成员执行。已经完成的结果与已消费历史仍可查看。
5. 在等待人工审批时重启服务，原执行中断，旧审批或补充信息回复不能续作；不恢复旧审批 Promise。用户需要时明确发起新工作。
6. 分别只重启 Gateway、只重启 Web bridge：Team 用户队列（包括仅有 teamSelection、尚未建立 activation 的输入）均失效；文本和附件引用保留。记录各服务 PID/instanceId，确认确实重启了目标进程。仅重启 Web bridge 的分支重点检查其用户队列，不将仍存活 Gateway 中的运行任务一概按重启中断处理；Gateway 恢复才检查步骤 3–5 的运行记录失效。普通聊天队列仍按原暂停恢复规则处理。只断开并重连浏览器或 bridge 到同一个 Gateway 的连接，不算进程重启，不应据此使有效 Team 输入失效。
7. 先保持无新人工输入，确认旧任务、消息和通知不会自动启动；再发送明确的新请求，仅要求读取已完成结果或执行一个新标记动作。核对新代次实际可用，同时旧副作用计数不变、旧 queued 工作没有被带着重跑。旧请求、旧回答和旧 token 的回放仍不能改变新执行。

**首次覆盖的功能：**

- [ ] F061：浏览器断线只影响观察，服务器仍执行；重开/刷新可恢复身份、任务、通信和结果。
- [ ] F062：已完成 Team 在服务重启后可读恢复，查看结果不产生新模型执行。
- [ ] F063：Gateway 恢复使旧代次全部未终结工作（含 queued）中断、全部待处理消息/通知失效，不自动唤醒 Leader；Gateway 或 Web bridge 进程重启使 Team 用户队列失效，明确的新请求不带着旧任务重跑。

### Case 21：自动续答有上限，通知失败不会丢失或重复执行

**方式：** 受控端到端。需要可控的成员完成节奏与通知接纳响应；不依赖真实模型自由聊天恰好产生足够轮次。

**操作与期望：**

1. 持续制造成员结果/消息。分别记录当前回合内应用的消息与真正启动的新 Leader 后续轮；前者不消耗自动唤醒额度。为触发上限，每次等 Leader 空闲并由通知启动后续轮，再释放下一批。
2. 默认运行段累计真正启动 24 次 Leader 自动后续轮后，再产生一个通知。后者应留在队列，面板出现自动续行暂停说明；再发一条新的人类输入，预算重置，待处理通知能够继续。
3. 单独设置故障：成员结果写入成功、通知发出前暂停，读回结果已持久化。分别模拟内部 mailbox 已入队但尚未写 transcript、已持久化且产生 steer_applied 但 runtime 确认丢失，以及空闲续轮输入持久化后确认丢失。前者不能提前标记已应用；后两者重试须核对稳定事件 ID 与 transcript，仅应用/接纳一次。单纯关闭浏览器不能制造该内部确认故障。
4. 恢复故障期间新增一条通知，不能改变前一批次的重试身份。确认所有通知最终均可查到，不能因重试在 Leader 历史重复插入相同输入。

**首次覆盖的功能：**

- [ ] F064：默认自动续答预算只计真正启动的 Leader 后续轮，上限 24；当前轮消息注入不消耗额度，达到上限明确暂停，新人工输入重置预算。
- [ ] F065：结果先持久化再通知；消息入队不提前确认应用，持久化应用/接纳边界及稳定事件身份防止响应丢失、并发重试和新增通知导致重复注入。

### Case 22：Team 数据缺失或损坏时明确报错

**方式：** 受控故障。使用 `fault-home`，先完成一次 Case 09 取得真实记录；停止服务、保留原文件后逐项注入故障，每个分支结束即还原，不混合损坏条件。

**操作与期望：**

1. 选一条有 Team 输入记录的聊天，暂时移走 runtime journal，启动后直接打开原 URL。Team 身份读取、发送、切换及历史修改应明确报错，不能把它当普通聊天运行。
2. 还原后单独损坏 runtime journal 的 JSON 或校验和，再尝试读取；保持报错，不覆盖原损坏证据。
3. 分别对配置库文件、活跃 Team 的主聊天 transcript 做对应损坏分支；配置不可读时不能当空配置库重建，活跃 Team 续聊检测到 transcript 解析错误时应拒绝提交。只读历史和退出 Team 后的普通续聊尚未统一执行该诊断，见已知问题，不宣称所有入口都能阻断。

**首次覆盖的功能：**

- [ ] F066：Team 身份/配置数据损坏不静默降级或覆盖原数据；活跃 Team 续聊检测到聊天记录解析错误时拒绝提交。
- [ ] F067：身份加载错误有可恢复的界面状态和重试入口，恢复成功后才重新开放操作。

### Case 23：保护 Team 历史与被引用项目

**方式：** 真实使用＋后端请求回放。项目操作限定为已备好的 P1、P2 和 `deletion-target`。

**操作与期望：**

1. 在有 Team 执行历史的聊天试用普通分叉、删除、重做最后一轮、改写历史；前端不可用或给出错误。回放对应接口仍须拒绝，不能只测菜单隐藏。
2. 在 Team 与普通聊天分别回放所有旧 `manage_checkpoints`/checkpoint HTTP 操作（含 list/diff、恢复、撤销及旧 Git 操作），均返回 `CHECKPOINTS_REMOVED`；HTTP 为 410，不读取备份、不恢复文件。原检查点 UI 不再出现，旧备份文件字节保持。这里被移除的是旧检查点接口承载的 Git 操作；Git 查看与操作走独立 `repository_operation`/现有 Git 路由，应仍正常。

- [ ] F069：项目删除检查配置及冻结运行引用，强制删除和检查失败都不能绕过；无引用项目仍按普通流程处理。

- [ ] F071：关键交互具有中英文文案及可用的键盘焦点/关闭行为。

### Case 25：旧配置升级后仍可使用，过渡启动逻辑不复活

**方式：** 升级环境端到端＋存储字节核对。使用已备好的 `legacy-home` 和 `legacy-backup-failure-home`；它们是旧格式样本，不能据此写“已验证线上升级”。

**操作与期望：**

1. 使用 `legacy-home` 启动当前服务，其中已有角色、Team、配置操作收据和旧启动收据。只打开配置库读取，原文件字节保持不变；界面只展示配置内容。
2. 通过 UI 保存一次合法配置，确认先生成完整旧数据备份，再转为当前格式；角色、Team 和原配置操作的重试语义保留。
3. 切换到 `legacy-backup-failure-home`，该样本已设置备份写入障碍；保存必须失败，原文件保持不变，不能先破坏旧数据再报错。
4. 旧启动收据、独立成员聊天绑定不能重新创建成员聊天；旧 `start`、`probe`、`conversation_get` 命令被拒绝。当前 `runtime_probe` 等命令与它们不同，不应一并禁用。

**首次覆盖的功能：**

- [ ] F072：旧配置读取不改写，首次修改先备份再迁移，备份失败保护原数据，配置收据保持有效。
- [ ] F073：已移除的过渡启动命令和成员聊天绑定不参与当前执行，不因升级恢复独立成员聊天。

## 4. 当前边界与已知问题

执行时用本节解释范围，不能将以下未支持功能计为漏测或通过：

- 当前没有独立成员聊天、成员直连开关、动态招募/删除运行成员、同角色多实例、Leader 自动审批、分层权限治理、在线蓝图编辑或甘特图。
- Leader 与运行中的 Teammate 使用内部邮箱，在安全边界处理消息；不能改写已发出的模型请求或拆开工具调用与结果。未强制 Leader 保持存活，也未增加 sleep/等待工具或改造 team_collect 轮询。面板刷新只读取状态。
- 能力设置约束工具接口、技能入口和 MCP 接入，不能代替操作系统沙箱。共享项目文件不天然隔离；禁止工具桥接口也不保证其他获授权执行接口无法操作同一文件。
- 服务仍运行时的浏览器刷新可恢复审批；Abort/服务重启使旧消息、通知、审批回复及未完成任务失效。共享目录没有整轮检查点锁，但也不再提供自动工作区快照/回滚承诺。
- 当前没有供用户设置自动续答预算的界面。Case 21 的默认上限为 24 次真正启动的 Leader 后续轮；开发测试若注入更小上限，只能算状态机辅助证据，不能声称验证了默认 24 次端到端行为。
- 截至此版本，配置页仍有“团队运行、任务委派和成员通信尚未实现”的过期说明；空默认工作区选项也仍写“所有成员必须固定项目”。实际上可以从模型菜单进入 Team，通用聊天可以在预检中选择执行项目。这两处是已发现的文案问题，验收应记录，不应据此判定运行功能不存在。
- transcript 损坏检查尚未统一覆盖只读历史及退出 Team 后的普通续聊；Case 22 对该项只验活跃 Team 提交时的检查，不把已知缺口列为已实现保护。
- 兼容性错误的 HTTP 状态码尚不完全统一，判定需结合真实 `code/message`；本文不预设所有冲突都返回 409。
